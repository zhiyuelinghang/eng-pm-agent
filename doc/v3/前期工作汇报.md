一、前期方案论证与资料搜集（耗时：8小时）

1、智能体运行底座调研（耗时：2.5小时）
（1）搜集并研读 NousResearch Hermes 开源项目资料，梳理其命令行交互、消息网关、定时任务、子智能体、MCP 集成等核心能力，明确其作为技能运行底座的定位。
（2）核实社区 HermesClaw 微信桥接方案，确认微信抽取、摘要等技能就运行在已部署的 Hermes 底座之上。
（3）纠正前期对 Hermes 定位的误判，确认其为"已部署、已在用的运行底座"，而非过渡性、可下线组件，为后续架构分层奠定基础。
（4）深入查阅 Hermes 仓库源码，确认其没有现成的任务状态 REST 接口，为任务跟踪方案的技术路线选择提供依据。

2、编排框架与技术栈调研（耗时：2.5小时）
（1）搜集 LangGraph 多步编排、状态机、审批催办闭环等能力资料，评估其作为上层编排层的适用性。
（2）调研 FastAPI、SQLAlchemy、Pydantic 等系统底座技术栈，确定对外服务框架选型。
（3）调研 PostgreSQL、Redis、Celery、MinIO 等开源组件，评估存储、缓存、异步任务与对象存储的开源方案。
（4）整理各组件的版本兼容性与社区活跃度，为开源优先的选型决策提供支撑。

3、部署方式与环境调研（耗时：1.5小时）
（1）调研 docker-compose 一键编排方案，评估本地与服务器统一部署的可行性。
（2）梳理容器端口规划与数据卷管理方式，规避端口冲突与数据丢失风险。
（3）整理服务器开发环境搭建所需的依赖清单与配置要点。

4、同类方案与场景资料搜集（耗时：1.5小时）
（1）搜集工程项目管理领域的信息流转、动态汇总、来源追溯等典型场景资料。
（2）整理三角色（核心链路、检索支撑、平台底座）协同的真实工作场景，作为方案验证依据。
（3）梳理前期需要验证的核心场景，形成场景清单的素材来源。

二、关键技术评估（耗时：6小时）

1、架构分层评估（耗时：2小时）
（1）评估并确定四层结构与各层职责：FastAPI 系统底座、LangGraph 上层编排、Hermes 执行底座、PostgreSQL/Redis/Celery/MinIO 数据与异步。
（2）评估各层的引入时机，明确第一阶段只用 Hermes，LangGraph 留到后期做多步、审批、催办流程时再上层引入。
（3）形成架构分层结论并落入产品方案文档。

2、编排框架取舍评估（耗时：1.5小时）
（1）对比 LangGraph 作为底层框架与作为上层编排层的差异，评估其复杂度与适用边界。
（2）得出结论：LangGraph 适合做多步、审批、催办的上层编排，不适合当系统底层框架。
（3）确定第一阶段先用 Hermes 现有串接跑通流程，避免过早引入复杂度。

3、任务跟踪可行性评估（耗时：1.5小时）
（1）针对跟踪 Hermes 任务状态的需求，评估轮询 Hermes 接口与上报模式两条技术路线。
（2）结合 Hermes 无任务状态接口的事实，确定第一版任务跟踪采用上报模式，由调用方主动上报每步状态入库。
（3）评估上报模式与已有数据表结构的契合度，确认无需新增表即可支撑。

4、部署与端口规划评估（耗时：1小时）
（1）评估并落实 docker-compose 一键部署方案。
（2）按要求将对外端口调整为非常用端口（PostgreSQL 15432、Redis 16379、MinIO 19000/19001、网关 18080），降低端口冲突与暴露风险。
（3）确认容器内部端口保持标准值，连接配置无需改动。
