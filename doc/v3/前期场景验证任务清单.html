三角色任务分工

围绕首个竖切与两个验证场景划分职责；下列条目为各角色需推进的事项，目标是验证可行性，而非交付完整模块。

角色 C · 核心链路

智能体与技能

将微信信息转化为项目动态摘要，首版先打通这条链路。

  • C1信息入口：微信群记录已抽取入库（♻️已实现），基于它跑通链路
  • C2信息抽取：从内容里识别项目、时间、人员、事项
  • C3技能-摘要：把一段信息整理成项目动态摘要
  • C4技能-待办提取：抽出责任人、事项、期限、来源打通后
  • C5技能-周报草稿：把事件/待办汇成一份可改的周报打通后
  • C6模型接入：DeepSeek/Qwen 调用，prompt 先置于配置文件中
  • C7人工确认（简单版）：结果先出草稿，经人工确认后生效
  • C8运行底座：微信抽取、摘要等 skill 都跑在已部署的 Hermes 上，第一阶段就用它
  • C9编排方式：第一阶段先用 Hermes 现有串接把这几步跑通，LangGraph 留到后面做多步/审批/催办流程时再上层引入

首版交付物

  • 一段真实微信信息 → 摘要，能存下来、能在页面看到
  • 结论：链路是否打通、抽取是否准确、存在哪些问题
角色 A · 检索支撑

知识库

让资料可录入、按项目检索，并使答案可追溯到来源。

  • A1文档解析：先把 PDF/Word/文本读进来，拿到正文
  • A2切片 + 入库：内容切块存起来，关联到项目
  • A3检索：PostgreSQL 全文检索先跑通，中文分词处理
  • A4带来源返回：结果带文件名和位置，供问答引用
  • A5按项目过滤：只返回该项目的资料（最小权限）
  • A6给 C 一个检索接口：search(问题, 项目) → 带来源结果
  • A7评估：pgvector 向量检索、RAGFlow 是否引入

首版交付物

  • 传一份资料能解析、能检索、能带来源
  • 给 C 的检索接口（可先返回模拟数据并约定格式）
角色 B · 平台底座

平台骨架

搭建最小基础环境，为 A、C 提供运行与存储支撑；后续 Web 端也由骨架继续开发。

  • B1FastAPI 骨架 + docker-compose 搭建本地环境
  • B2PostgreSQL + MinIO 部署就绪，可连接、可存储
  • B3最小表：用户、项目、项目成员、原始信息、文件
  • B4登录 + 当前用户能看哪些项目（最小权限）
  • B5项目 / 成员接口：可创建项目、添加成员
  • B6信息写入接口：C 把摘要写进来（待办/周报字段预留）
  • B7简单 Web 展示页：登录 → 看项目下的摘要，用于功能演示
  • B8技能调用记录：skill 调用有日志（最小版）

首版交付物

  • 一键起环境，能登录、建项目
  • 一个简单 Web 页：能把 C 产出的摘要存下来并展示

验证成功标准（重在实用，而非功能齐全）

  • 减负 项目经理认可摘要节省了整理时间，愿意持续使用
  • 提效 待办能被自动抽取，无需人工逐条翻阅消息查找
  • 管住风险 项目状态问答能带来源回答，不编造、不越权
