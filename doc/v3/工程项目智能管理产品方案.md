# 工程项目智能管理产品方案

## 1. 核心结论

这个产品的定位不应该是“工程知识库 + 问答系统”，而应该是：

```text
工程项目智能管理产品
= 项目智能秘书 + 项目群智能监管 + 工程知识底座 + 权限与留痕体系
```

知识库是底座，问答是入口，项目管理事务推进才是核心价值。

这个产品要做的不是把资料放进去让用户提问，而是让智能体围绕项目进展主动工作：

```text
自动收集项目信息
自动整理项目动态
自动提取待办事项
自动提醒责任人
自动生成日报周报
自动跟踪整改闭环
自动检查资料缺失
自动识别长期无更新和节点逾期
自动沉淀项目过程知识和经验
```

最终要达到的效果是：

```text
让项目经理、总工、工程部长少写材料、少翻记录、少漏任务、少整理资料；
让工程管理部门更快看清项目状态、发现风险、跟踪整改、追溯依据；
让少数核心管理人员通过智能体管理更多项目，并且管得更清楚、更规范、更可追溯。
让 2—3 个核心人员也能在智能体辅助下承担过去更多人才能完成的信息收集、资料整理、任务提醒、报告生成和风险跟踪工作。
```

---

## 2. 产品本质

这个产品的本质是工程项目管理过程中的“信息处理层”和“事务推进层”。

传统项目管理中，大量工作不是专业决策本身，而是事务性、重复性、分散性的管理动作：

```text
看群消息
翻邮件
整理会议纪要
汇总日报
催整改
查资料
找依据
写周报
跟踪待办
检查项目有没有更新
判断哪些项目可能有风险
```

这些工作消耗项目经理、总工、工程部长和工程管理部门大量时间，但很多动作具有明显的规律性，适合由智能体辅助完成。

所以这个产品的核心不是做一个“会回答问题的知识库”，而是做一个能参与项目管理过程的智能助手：

```text
项目发生了什么，它能看见；
哪些事情需要跟进，它能提取；
谁该处理什么，它能提醒；
哪些资料缺失，它能检查；
哪些问题逾期，它能发现；
项目状态如何，它能汇总；
结论来自哪里，它能追溯。
```

## 3. 目标用户和核心价值

### 3.1 施工单位用户

主要用户包括：

```text
项目经理
项目总工
工程部长
技术负责人
质量员
安全员
资料员
生产经理
```

他们最痛的不是“没有知识库”，而是：

```text
每天信息太散，微信群、邮件、文件、会议记录到处都是。
每天要写材料，日报、周报、汇报、整改回复反复整理。
任务容易漏，群里一句话、会上一个要求，很容易没人跟。
资料难归档，过程资料产生了但没有进入正式管理体系。
问题难闭环，整改发出去了但谁负责、何时完成、证据在哪里不清楚。
管理人员减少，但项目管理要求没有减少。
```

产品给施工单位的价值是：

```text
少写材料
少翻记录
少漏任务
少催进度
少整理资料
更容易形成过程留痕
更容易把经验沉淀下来
```

### 3.2 建设方用户

主要用户包括：

```text
工程管理部门
项目负责人
建设单位工程部长
质量安全管理人员
公司级项目监管人员
```

他们最痛的是：

```text
项目多，人工逐个盯不过来。
项目真实状态不透明，只能靠汇报材料判断。
风险项目发现晚，逾期整改和长期无更新容易被掩盖。
资料完整性难检查，缺资料往往到验收或检查时才暴露。
问题整改缺少连续追踪，责任、节点、证据不够清楚。
```

产品给建设方的价值是：

```text
看清项目状态
发现风险项目
跟踪整改闭环
识别逾期和长期无更新
检查资料完整性
追溯每个结论的依据
提升多项目监管效率
```

## 4. 两个真实场景闭环

前期应该围绕第一阶段的最小闭环验证价值，而不是先做一个很重、很完整的平台。

### 4.1 场景一：施工单位项目智能秘书

定位：项目经理、总工、工程部长身边的智能秘书。

它要围绕单个项目的日常管理工作，帮助项目团队自动整理信息、提取待办、生成材料、跟踪问题和沉淀资料。

核心能力：

| 能力 | 说明 |
|---|---|
| 微信群/企业微信摘要 | 自动整理群内项目动态、问题、通知、决策、待办 |
| 邮件摘要 | 自动识别邮件中的项目事项、附件、回复要求和时间节点 |
| 待办提取 | 从群消息、邮件、会议纪要、整改通知中提取责任人、事项、期限 |
| 日报生成 | 根据当天消息、任务、现场记录、图片和资料生成日报草稿 |
| 周报生成 | 汇总一周项目进展、问题、风险、整改、下周计划 |
| 资料归档 | 将群文件、邮件附件、日报周报、会议纪要归入项目知识库 |
| 整改闭环 | 跟踪问题提出、责任分配、整改回复、证据上传、复核关闭 |
| 项目问答 | 基于项目资料、规范、历史记录回答项目相关问题 |

典型工作流：

```text
微信群/邮件/文件进入系统
	-> 自动识别项目、时间、人员、事项、附件
	-> 生成项目事件和待办
	-> 需要确认的内容推送给项目经理/责任人
	-> 确认后进入任务列表和资料库
	-> 到期前自动提醒
	-> 完成后收集证据并形成闭环记录
	-> 自动汇总到日报、周报和项目知识库
```

这个场景的成功标准不是“问答有多聪明”，而是：

```text
项目经理每天少整理多少信息；
日报周报能否自动生成可用草稿；
群里和邮件里的待办是否能被提取出来；
整改事项是否能被持续跟踪；
资料是否能自然沉淀到项目库；
项目团队是否愿意每天用它。
```

### 4.2 场景二：建设方项目群智能监管

定位：工程管理部门的项目群监管助手。

它要面向多个项目，帮助管理部门看清项目状态、识别异常项目、跟踪整改和追溯依据。

核心能力：

| 能力 | 说明 |
|---|---|
| 项目看板 | 展示项目进度、风险、待办、整改、资料完整性和更新状态 |
| 风险项目识别 | 根据逾期、长期无更新、整改反复、资料缺失等规则识别风险项目 |
| 逾期整改跟踪 | 自动列出逾期问题、责任单位、责任人、逾期天数和证据状态 |
| 长期无更新提醒 | 发现项目日报、进度、资料、问题记录长时间没有更新 |
| 资料完整性检查 | 检查项目关键资料是否缺失、过期、未审核或未归档 |
| 项目状态问答 | 管理人员可以直接问“哪个项目风险最高”“某项目整改到哪一步了” |
| 监管报告生成 | 自动生成项目群周报、风险清单、整改跟踪表和管理摘要 |

典型工作流：

```text
多个项目持续产生消息、资料、任务和整改记录
	-> 系统形成项目事件流和任务状态
	-> 按项目汇总进度、质量、安全、资料、整改情况
	-> 自动识别异常项目和风险事项
	-> 推送给工程管理部门
	-> 管理人员查看依据、追问细节、下发督办
	-> 督办结果继续进入闭环和知识沉淀
```

这个场景的成功标准是：

```text
管理部门能否更早发现风险项目；
逾期整改是否一眼可见；
长期无更新项目是否能自动暴露；
项目状态是否能用依据解释；
多项目监管是否减少人工汇总成本。
```

## 5. 产品能力三层

经理提出的三层能力更适合作为产品总框架。

这三层不是阶段，也不是用户分类，而是产品能力从低到高的结构：先知道项目发生了什么，再推动项目该做什么，最后辅助项目怎么做得更好。

| 层级 | 核心问题 | 能力重点 |
|---|---|---|
| 第一层 | 知道项目发生了什么 | 信息采集、资料整理、项目摘要、状态问答 |
| 第二层 | 推动项目该做什么 | 待办提取、节点提醒、整改闭环、资料缺失提醒、日报周报生成 |
| 第三层 | 辅助项目怎么做得更好 | 方案审核、质量安全风险识别、技术参数校核、类似项目经验推荐、专业技术辅助决策 |

### 5.1 第一层：知道项目发生了什么

这一层解决“项目状态不透明、信息分散、资料难找”的问题。

平台要能从项目日常信息源中收集内容，包括：

```text
企业微信群/项目群消息
邮件正文和附件
上传文件
会议纪要
日报周报
整改通知
现场照片和记录
已有业务系统接口
```

然后把原始消息和文件整理成可理解、可查询、可追溯的项目状态。

这一层的核心能力是：

```text
信息采集
资料整理
项目摘要
项目状态问答
资料来源追溯
项目事件沉淀
```

重要边界：普通微信群的自动采集存在平台开放能力和合规限制，优先建议从企业微信、钉钉、邮件、文件上传和人工转发入口做起。普通微信群可以通过合规的转发、导出或项目助手账号方式接入，不能把技术不可控的入口作为唯一主链路。

### 5.2 第二层：推动项目该做什么

这一层解决“事情没人跟、任务容易漏、整改不闭环、资料缺失没人提醒”的问题。

平台要把信息变成可推进的任务，而不是只停留在摘要和问答。

这一层的核心能力是：

```text
待办提取
节点提醒
整改闭环
资料缺失提醒
日报周报生成
会议决议跟踪
风险事项跟进
```

每个被系统提取出来的任务都应该有：

```text
来源
责任人
截止时间
状态
提醒记录
处理结果
证据材料
复核人
关闭时间
```

这一层是产品从“知道项目”变成“推进项目”的关键。

### 5.3 第三层：辅助项目怎么做得更好

这一层解决“项目管理和工程技术决策需要专业支持”的问题。

当系统已经能掌握项目状态、任务、资料和历史过程之后，才能进一步提供专业辅助。

这一层的核心能力是：

```text
方案审核
质量安全风险识别
技术参数校核
类似项目经验推荐
专业技术辅助决策
规范条文匹配
问题模式识别
项目管理策略建议
```

这一层不能脱离前两层单独存在。没有项目过程数据、资料来源和任务状态，专业建议就容易变成空泛的模型回答。

### 5.4 三层能力和产品价值的关系

产品价值可以这样理解：

```text
第一层让系统看得见项目。
第二层让系统推得动项目。
第三层让系统帮项目做得更好。
```

所以产品不是“知识库 + 问答”，而是：

```text
项目感知能力
+ 项目事务推进能力
+ 专业技术辅助能力
```

## 6. 总体架构

### 6.1 架构总览

```text
项目消息/邮件/文件/业务系统
				|
				v
信息采集层：企业微信/钉钉/邮件/上传/接口适配器
				|
				v
信息理解层：消息解析、附件解析、项目识别、事项提取、证据抽取
				|
				v
项目事件中心：Project Event、Todo、Issue、Evidence、Report Material
				|
				+--------------------+
				|                    |
				v                    v
任务推进系统             知识与检索系统
待办/整改/提醒/闭环       文档/索引/关系/引用/权限
				|                    |
				+----------+---------+
									 v
应用服务层：FastAPI 权限内核 + Skill Registry + Tool Gateway + 状态机
									 |
				+----------+----------+
				|                     |
				v                     v
项目智能秘书入口        项目群智能监管看板
Bot/Web/小程序           Web 看板/后台/问答
```

### 6.2 核心分层

| 层级 | 作用 | 建议技术 |
|---|---|---|
| 交互入口 | 用户对话、查看看板、确认任务、上传资料 | 企业微信/钉钉 Bot、Web、小程序可选 |
| 信息采集层 | 接入群消息、邮件、文件和业务系统数据 | Adapter 服务、IMAP/API、Webhook、上传接口 |
| 信息理解层 | 摘要、分类、事项提取、责任人识别、期限识别 | LLM + 规则 + Python 解析器 |
| 项目事件中心 | 把信息沉淀为项目事件、任务、证据 | FastAPI + PostgreSQL |
| 知识底座 | 知识入库、检索、关联、引用追溯 | PostgreSQL FTS/pgvector + MinIO/OBS |
| 任务推进层 | 待办、整改、提醒、闭环、报告生成 | Skill Registry + DB 状态机 + Celery/APScheduler |
| 权限与审计 | 用户、角色、项目权限、日志、证据链 | FastAPI + PostgreSQL（权限与状态内核）|
| 项目看板 | 项目状态、风险、逾期、资料完整性 | Web 工作台（React + Ant Design）|

## 7. 数据底座

核心数据不是只有知识文档，而是项目管理过程数据。

### 7.1 核心对象

| 对象 | 说明 |
|---|---|
| user | 用户账号 |
| org | 组织、部门、单位 |
| role | 角色，如项目经理、总工、工程部长、安全员 |
| project | 项目 |
| project_member | 用户在项目中的身份和权限 |
| source_message | 原始消息，如群消息、邮件正文 |
| source_file | 原始文件，如附件、图片、文档 |
| project_event | 项目事件，如进度更新、质量问题、会议决议 |
| project_todo | 待办事项 |
| rectification_issue | 整改问题 |
| report_record | 日报、周报、监管报告 |
| knowledge_doc | 知识文档 |
| knowledge_chunk | 检索切片 |
| knowledge_relation | 知识、任务、项目、问题之间的关系 |
| evidence_record | 引用依据和证据链 |
| skill_run_log | 技能执行记录 |
| audit_log | 权限、操作、工具调用审计 |

### 7.2 为什么要有项目事件中心

如果只做知识库，系统只能回答“资料里写了什么”。

但项目智能管理产品必须回答：

```text
项目最近发生了什么？
哪些事情还没完成？
谁该处理？
什么时候到期？
证据在哪里？
是否已经闭环？
是否形成风险？
```

这些问题必须依赖项目事件、任务状态和证据链，所以 `project_event`、`project_todo`、`rectification_issue`、`evidence_record` 是产品的核心数据。

## 8. 技能体系

智能能力应该优先做成可控技能，而不是一开始依赖自由 Agent 自主发挥。

### 8.1 核心技能清单

| 技能 | 输入 | 输出 |
|---|---|---|
| 群消息摘要 | 群消息、时间范围、项目 | 项目动态摘要、待办候选、风险提示 |
| 邮件摘要 | 邮件正文、附件 | 事项摘要、待办候选、附件归档建议 |
| 待办提取 | 消息、邮件、会议纪要 | 责任人、事项、期限、来源 |
| 日报生成 | 当日事件、待办、资料、图片 | 日报草稿 |
| 周报生成 | 本周事件、整改、风险、计划 | 周报草稿 |
| 整改跟踪 | 问题、责任人、期限、证据 | 整改状态、逾期提醒、闭环记录 |
| 资料完整性检查 | 项目资料目录、标准清单 | 缺失资料、过期资料、未审核资料 |
| 风险项目识别 | 多项目事件、任务、整改、资料 | 风险项目列表和原因 |
| 项目状态问答 | 用户问题、项目权限、项目数据 | 带依据的回答 |
| 规范依据查询 | 问题、规范库、项目场景 | 相关条款和引用来源 |

### 8.2 技能执行原则

每个技能都必须：

```text
有明确输入
有明确输出
有执行状态
有来源引用
有权限校验
有日志记录
必要时有人确认
不能绕过系统直接修改正式业务数据
```

### 8.3 Agent 的正确定位

Agent 不应该成为一开始的主架构。

更合理的定位是：

```text
用户说一句话
	-> Agent/路由器判断意图
	-> 调用已注册技能
	-> 技能读取项目事件、知识和任务状态
	-> 生成结果
	-> 需要时让人确认
	-> 状态和证据回写数据库
```

也就是说，Agent 是入口和调度者，Skill 才是业务动作单元，PostgreSQL 才是正式状态来源。

## 9. 权限、留痕与可信边界

权限、知识管理、后台、日志、追溯这些能力要保留，但前期只做到支撑场景闭环所必需的程度。

### 9.1 权限原则

```text
用户只能看到自己有权访问的项目。
用户只能查询自己有权访问的资料。
用户只能查看自己有权查看的任务和整改。
问答检索前必须做权限过滤。
答案返回前必须做引用来源权限复核。
高风险操作必须人工确认。
```

### 9.2 留痕原则

平台必须记录：

```text
原始消息来源
原始文件来源
任务从哪里提取
报告依据哪些事件生成
回答引用哪些资料
技能何时执行
谁确认了结果
谁关闭了任务
哪些提醒已经发送
```

### 9.3 可信边界

系统不能做这些事：

```text
不能无依据生成正式结论。
不能把用户无权限资料放进回答。
不能让模型直接修改正式业务系统。
不能让 Agent 自由调用未知工具。
不能把群消息自动当成已确认事实。
不能把未审核资料直接当成正式知识。
```

## 10. 平台后台定位

前期不能一上来做很重的平台后台，但也不能没有后台底座。

后台的定位应该是“支撑场景闭环的最小管理台”，而不是先做完整大平台。

最小后台需要支持：

```text
用户管理
项目管理
角色和项目授权
知识库配置
资料入库审核
任务和整改列表
风险规则配置
技能配置
消息源配置
执行日志查看
```

推荐方式：

```text
Web 工作台内置管理配置（用户、项目、权限、规则、审核）。
FastAPI 做真正的权限内核、任务状态、知识检索和技能执行。
PostgreSQL 做统一数据底座。
```

这样把管理配置收进 Web 工作台，后台只做支撑场景闭环所必需的最小管理页，不把后台做成一个过重工程。

Hermes Web、AgentScope Web 这类工具不能作为业务后台主底座，它们更适合做 Agent 调试、运行入口或后续编排平台。

## 11. 技术链推荐

### 11.1 前期主链路技术

| 模块 | 推荐技术 | 作用 |
|---|---|---|
| 后端内核 | FastAPI + Pydantic + SQLAlchemy + Alembic | API、权限、任务、技能、审计 |
| 主数据库 | PostgreSQL 16 | 项目、用户、任务、知识、证据、日志 |
| 检索能力 | PostgreSQL FTS + pgvector | 文档全文检索和向量检索 |
| 文件存储 | MinIO / S3 / 云 OBS | 原始文件、附件、图片、报告存储 |
| 异步任务 | Celery + Redis | 解析、摘要、索引、报告生成、提醒 |
| 定时任务 | APScheduler / Celery Beat | 周报、逾期检查、长期无更新检查 |
| 消息入口 | 企业微信/钉钉 Bot、邮件 IMAP/API、文件上传 | 项目信息采集 |
| Web 工作台与后台 | React + Ant Design | 看板、任务、报告、问答，内置用户、项目、权限、审核、规则配置 |
| 前端看板 | React + Ant Design | 项目看板、风险列表、整改跟踪 |
| 模型服务 | DeepSeek/Qwen 等国产模型 | 摘要、提取、问答、报告草稿 |
| 技能系统 | Python Skill Registry | 固定技能封装和统一调用 |

### 11.2 可选增强技术

这些技术可以预留接口，但不应压到前期主链路：

| 技术 | 适合解决的问题 | 当前定位 |
|---|---|---|
| RAGFlow 等开源知识库 | 文档解析、切片、索引、检索问答 | 第一阶段即可评估接入，但不能替代项目事件中心、权限内核和任务状态 |
| LangGraph | 多步骤、长流程、需要人机协同的任务编排 | 上层编排骨架；第一阶段不引入，后续做多步/审批/催办闭环时再上（详见 11.4） |
| Hermes | 智能体/技能的运行底座，承载微信抽取、摘要等 skill | 已部署、已在用；是 C 角色的执行环境，第一阶段即靠它，与 LangGraph 上下层配合（详见 11.4） |
| AgentScope | 多 Agent、多会话、Agent 服务化 | 已决定不采用，编排统一用 LangGraph |
| Neo4j/GraphRAG | 复杂知识关系和跨项目推理 | 知识关系规模变大后再上 |
| LiteLLM | 多模型网关、限流、成本控制 | 多模型同时使用时接入 |
| Langfuse/Phoenix | Prompt、Trace、效果评估 | 模型调用变多后接入 |
| Temporal | 长周期任务和失败补偿 | 状态机复杂后替换或增强 |

### 11.3 技术选型结论

```text
主线：FastAPI + PostgreSQL + Redis/Celery + MinIO + Web 工作台（React + Ant Design）+ 企业微信/邮件入口 + Python Skill Registry

检索：PostgreSQL FTS 起步，结合 pgvector 做混合检索

问答：所有问答必须经过权限过滤、引用追溯和结果复核

任务：所有待办、整改、报告、提醒都进入数据库状态机

后台：只做支撑场景闭环的最小后台，不先做重平台

Agent：先作为意图识别和技能调度入口，不作为自由自治主体
```

### 11.4 编排框架与 Hermes 决策记录

这是一个明确的架构决策，避免团队对“编排到底用什么、Hermes 要不要”反复纠结。

**编排骨架：选定 LangGraph，弃用 AgentScope。**
原因：审批、催办、问题闭环这些是确定性状态流转，LangGraph 的“显式图 + 持久状态 + 断点续跑”最匹配；生态最大、招人好接、长期维护成本低。两个编排框架只留一个，避免功能重叠。

**Hermes：是智能体与技能的运行底座（已部署、已在用），不是要被替换或下线的过渡件。**
微信抽取、信息摘要等 skill 都跑在它上，第一阶段验证就依赖它。它和 LangGraph 是上下层分工，不二选一：

| 层 | 谁 | 职责 |
|---|---|---|
| **执行底座** | **Hermes（已在用）** | 承载并运行各项 skill（微信抽取、摘要等），第一阶段就靠它 |
| **上层编排** | **LangGraph（后续引入）** | 串多步、有状态、要审批/催办/闭环的复杂流程 |

阶段节奏：

| 阶段 | 编排怎么做 |
|---|---|
| **第一阶段（验证打通）** | 用 Hermes 现有串接把“微信→摘要→存储→展示”跑通，不引入 LangGraph |
| **后续（复杂流程）** | 上层加 LangGraph 编排多步/审批/催办，skill 仍跑在 Hermes 上 |

**一句话：Hermes 是 skill 运行底座、已在用；LangGraph 是上层复杂流程编排、后续按需引入；两者上下层配合，不是替换关系。**

## 13. 验收标准

产品是否成功，不应只看模型回答是否流畅，而要看是否真正减负、提效、管住风险。

### 13.1 施工单位验收

```text
能否自动生成可用的微信群/邮件摘要。
能否从消息和邮件中提取待办事项。
能否生成项目经理可修改后使用的日报、周报草稿。
能否跟踪整改事项从提出到关闭。
能否把过程资料归档到项目知识库。
能否回答项目经理关于任务、资料、整改和依据的问题。
```

### 13.2 建设方验收

```text
能否展示多个项目当前状态。
能否识别逾期整改和长期无更新项目。
能否检查关键资料缺失。
能否生成风险项目清单。
能否回答项目状态、风险原因、整改进度等问题。
能否追溯每个风险判断和报告结论的依据。
```

### 13.3 底座验收

```text
权限不会泄露。
答案有引用来源。
任务有状态。
技能有日志。
报告有依据。
高风险动作有人确认。
原始消息、文件、任务、报告之间可以追溯。
```

## 14. 风险与处理

| 风险 | 处理方式 |
|---|---|
| 把产品做成单纯知识库问答 | 所有能力围绕项目事件、任务、整改、报告和看板闭环设计 |
| 一开始后台做太重 | 后台只做支撑场景闭环的最小管理能力 |
| 群消息接入不可控 | 优先企业微信/钉钉/邮件/上传，普通微信群走合规转发或导出方案 |
| 模型提取待办不准确 | 模型提取 + 规则校验 + 人工确认，不直接进入正式任务 |
| 权限泄露 | 检索前过滤、返回前复核、日志审计 |
| 报告编造 | 报告必须基于项目事件、任务状态和引用证据生成 |
| 整改无法闭环 | 每个整改必须有责任人、期限、状态、证据和复核记录 |
| 资料归档变成垃圾库 | 入库状态、审核状态、项目分类、来源追溯必须保留 |
| Agent 失控 | 只允许调用注册技能和受控工具，高风险动作人工确认 |

## 15. 最终定位表达

对内可以这样描述这个产品：

```text
它不是做一个单纯的工程知识库，也不是做一个聊天机器人。

它是面向施工单位和建设方的工程项目智能管理产品。

知识库是底座，问答是入口，项目管理事务推进是核心价值。

它通过自动整理群消息和邮件、提取待办、生成日报周报、跟踪整改闭环、检查资料缺失、识别风险项目和沉淀过程知识，帮助项目经理、总工、工程部长和工程管理部门用更少的人把项目管得更清楚、更规范、更可追溯。

技术上以 FastAPI + PostgreSQL 为权限和状态内核，以 Web 工作台（React + Ant Design）作为唯一正式入口并内置管理配置，以企业微信/邮件/文件入口采集项目信息，以 Skill Registry 封装可控技能，以知识检索和证据链保证答案与报告可追溯，后续再按需要接入 RAGFlow、LangGraph、AgentScope、GraphRAG 等增强能力。
```

最短的一句话：

```text
这是一个以项目智能秘书和项目群智能监管为核心的工程项目智能管理产品。
```

## 16. 阶段目标划分

建议分成四个阶段。阶段是严格的 1 -> 2 -> 3 -> 4 顺序推进。

这里的阶段不是按施工单位、建设方、用户角色来拆，也不是按单个技术组件来拆，而是按开发团队要交付的产品能力成熟度来拆：

```text
第一阶段：把核心闭环跑通，证明产品能用。
第二阶段：把单项目能力做稳，证明产品能持续用。
第三阶段：把多项目管理做起来，证明产品能规模化用。
第四阶段：把专业智能和行业经验沉淀出来，证明产品有长期壁垒。
```

### 16.1 阶段一：核心闭环 MVP

阶段目标：做出一个最小可用产品，把“信息进入 -> 事项识别 -> 任务推进 -> 报告生成 -> 风险提示 -> 依据追溯”这条核心链路跑通。

#### 做什么

```text
1. 做项目信息入口：消息、邮件、文件、人工上传。
2. 做项目事件中心：把原始信息变成项目事件、待办、整改、证据。
3. 做任务状态机：待确认、待处理、处理中、待复核、已关闭。
4. 做核心技能：摘要、待办提取、日报周报草稿、整改跟踪、项目状态问答。
5. 接入或评估开源知识库能力：文档解析、切片、索引、检索问答。
6. 做最小知识权限边界：资料元数据、项目权限、引用来源、返回前复核。
7. 做最小后台：用户、项目、权限、任务列表、资料审核、日志查看。
```

#### 怎么做

```text
1. 后端用 FastAPI 承担权限、项目、任务、知识、技能和日志 API。
2. 数据用 PostgreSQL 保存项目、事件、任务、资料、证据和审计日志。
3. 异步任务用 Celery/Redis 处理解析、摘要、索引、提醒和报告生成。
4. 文件用 MinIO/OBS 保存原始附件、图片和报告。
5. 知识库优先评估 RAGFlow 等开源项目，能复用文档解析、切片、索引和检索问答能力就不要从零写。
6. FastAPI 仍掌握项目权限、项目事件、任务状态、证据链和对外 API，不让开源知识库成为业务状态中心。
7. 管理配置放进 Web 工作台，只做支撑闭环所需的最小管理页，不做重后台。
8. 模型只调用注册 Skill，不让 Agent 自由执行未知动作。
9. 所有结果先进入草稿或待确认状态，高风险动作必须人工确认。
```

#### 成功标准

```text
1. 信息能进入系统，并能自动归属到项目。
2. 系统能从消息、邮件、文件中提取项目事件和待办候选。
3. 待办、整改、报告都有状态和负责人。
4. 日报、周报、整改跟踪能生成可修改草稿。
5. 项目状态问答能带依据回答，不编造、不越权。
6. 任务、报告、问答、技能调用都有日志和来源追溯。
7. 开发团队能用这套闭环向业务方证明产品不是聊天机器人，而是在推进项目事务。
```

### 16.2 阶段二：项目级产品化

阶段目标：把第一阶段跑通的核心闭环做稳定、可配置、可复用，让系统可以在真实项目中持续运行。

#### 做什么

```text
1. 完善项目事件中心，统一事件、任务、整改、资料、报告的数据模型。
2. 完善任务协同，支持责任人、截止时间、提醒、复核、关闭和延期。
3. 完善报告体系，支持日报、周报、会议纪要、整改清单模板配置。
4. 完善知识入库，支持资料分类、审核、版本、失效、引用关系。
5. 完善权限体系，支持组织、项目、角色、资料范围和操作权限。
6. 完善后台配置，支持消息源、技能、规则、模板、项目参数配置。
7. 完善稳定性，补齐异常处理、重试、失败告警和人工修正入口。
```

#### 怎么做

```text
1. 把阶段一的原型数据表整理成稳定领域模型。
2. 把 Skill Registry 做成可配置、可观测、可回放的技能体系。
3. 把提示词、模板、规则从代码中抽离到配置表或后台配置。
4. 为关键技能增加测试集和人工评价机制。
5. 增加任务看板、报告草稿列表、资料审核列表、项目事件列表。
6. 增加权限回归测试，保证换角色、换项目后数据范围正确。
7. 引入更稳定的混合检索：PostgreSQL FTS + pgvector + rerank 可选。
```

#### 成功标准

```text
1. 一个项目可以连续使用，不依赖开发人员手工兜底。
2. 项目事件、任务、资料、报告之间能稳定关联。
3. 常用报告草稿达到可编辑、可提交、可追溯的水平。
4. 权限、日志、证据链成为系统默认能力，而不是临时补丁。
5. 新增一个项目时，主要通过配置完成，不需要重新开发。
6. 关键技能失败时能定位原因，能重试，能人工修正。
```

### 16.3 阶段三：多项目监管与组织级平台

阶段目标：从单项目运行升级到多项目统一管理，让系统具备组织级项目监管、横向对比和风险识别能力。

#### 做什么

```text
1. 做多项目总览：项目状态、进度、风险、整改、资料完整性。
2. 做风险识别：逾期、长期无更新、资料缺失、问题反复、节点异常。
3. 做跨项目汇总：整改清单、风险清单、资料缺失清单、周报/月报。
4. 做组织级权限：公司、部门、区域、项目、角色、数据范围。
5. 做经验复用：同类问题、典型案例、处理方式、制度依据沉淀。
6. 做外部系统集成：项目管理、质量安全、资料管理、OA、消息通知。
```

#### 怎么做

```text
1. 在 PostgreSQL 中建立组织级项目指标和风险指标表。
2. 建立项目健康度、资料完整性、整改闭环率、更新频率等计算任务。
3. 用定时任务生成项目日报、周报、月报和风险快照。
4. 对接更多项目数据源，形成统一项目事件流。
5. 增加多项目驾驶舱和风险列表，不再只看单项目页面。
6. 引入 Langfuse/Phoenix 或类似工具观察模型和技能效果。
7. 如果第一阶段已接入 RAGFlow 等知识库能力，这一阶段扩展其多项目知识服务；复杂流程确实需要时再评估 LangGraph。
```

#### 成功标准

```text
1. 多个项目可以统一看板展示，并能下钻到依据。
2. 系统能自动暴露逾期、长期无更新、资料缺失和高风险项目。
3. 管理汇总不再主要依赖人工收集材料。
4. 同类问题能跨项目复盘，并能沉淀为经验知识。
5. 组织级权限清晰，不同部门和角色看到的数据范围正确。
6. 项目监管报告能自动生成，并且结论可追溯。
```

### 16.4 阶段四：行业级智能管理产品

阶段目标：从项目管理工具升级为有专业能力、有行业经验、有智能协作能力的工程管理产品。

#### 做什么

```text
1. 做工程风险知识图谱，沉淀项目、问题、规范、方案、案例之间的关系。
2. 做专业技术辅助，如施工方案审查、规范条文匹配、质量安全风险提示。
3. 做行业经验库，把跨项目问题、整改方式、管理策略沉淀为可复用资产。
4. 做复杂任务编排，支持跨系统、跨角色、跨时间周期的长流程任务。
5. 做多智能体协作，让不同智能体承担资料、风险、技术、报告、监管等职责。
6. 做企业级治理，包括模型治理、成本治理、审计合规、效果评估。
```

#### 怎么做

```text
1. 将 knowledge_relation 扩展为图谱能力，可评估 Neo4j/GraphRAG。
2. 将复杂流程从简单状态机升级为 LangGraph 或 Temporal。
3. 将多 Agent 运行时接入到统一权限、工具网关和任务状态之后。
4. 引入 LiteLLM 做模型网关，统一模型、限流、成本和供应商切换。
5. 引入 Langfuse/Phoenix 做 Prompt、Trace、效果评估和质量回归。
6. 建立行业模板库、规则库、案例库和专业评测集。
```

#### 成功标准

```text
1. 系统不只是整理项目事务，还能提供专业辅助判断。
2. 跨项目经验能复用到新项目、新问题和新报告中。
3. 复杂任务可以跨人、跨系统、跨天稳定推进。
4. 多智能体能力受统一权限、工具网关、状态机和审计约束。
5. 产品形成行业模板、专业知识、历史案例和工作流沉淀。
6. 系统具备可复制、可部署、可运营、可持续优化的产品形态。
```

### 16.5 阶段划分总览

| 阶段 | 名称 | 做什么 | 怎么做 | 成功标准 |
|---|---|---|---|---|
| 阶段一 | 核心闭环 MVP | 信息入口、事件中心、任务状态、报告草稿、开源知识库接入评估、最小管理页 | FastAPI + PostgreSQL + Celery + MinIO + Web 工作台（React + Ant Design）+ RAGFlow 可选 + Skill Registry | 核心链路能跑通，结果有状态、有依据、有日志 |
| 阶段二 | 项目级产品化 | 模板、规则、权限、归档、报告、任务协同稳定化 | 配置化、测试集、权限回归、技能观测、异常处理 | 单项目可以持续使用，新项目主要靠配置接入 |
| 阶段三 | 多项目管理平台 | 多项目看板、风险识别、跨项目汇总、组织权限、经验复用 | 指标计算、风险规则、项目驾驶舱、系统集成、模型观测 | 多项目状态可视、风险自动暴露、报告自动生成 |
| 阶段四 | 行业级智能产品 | 专业辅助、知识图谱、复杂编排、多智能体、行业模板 | GraphRAG/Neo4j、LangGraph/Temporal、LiteLLM、Langfuse、评测集 | 形成专业能力、行业经验和可持续运营的产品壁垒 |
