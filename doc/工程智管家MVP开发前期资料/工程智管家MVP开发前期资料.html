01

总体建设方案

产品定位、建设目标、MVP 闭环、系统边界、阶段规划

建设背景

项目一线已同时使用公司平台、股份平台、业主平台、检测平台、小程序、在线表格和微信群。系统越多，现场反而越累：

  • 平台多、填报入口多，同类信息重复录入
  • 微信群、日报、照片、监测资料、平台表单之间缺少联动
  • WBS 计划和风险源清单已存在，但没有主动提醒和任务分派
  • 日报文件能下载，但仍需人工阅读、整理、提取
  • 风险上报、节点变更、材料上传仍靠人工复制粘贴
目标不是再造一个新平台，而是在现有平台和项目一线之间建立一个智能工作层。

产品定位与核心价值

面向项目一线的进度风险提醒与填报减负智能体。承担“信息整理、风险提醒、任务推进、草稿生成、辅助填报”，不替代各既有平台。

少填报
从 WBS、风险清单、日报、附件提取信息，减少重复录入
早提醒
按 WBS 工序计划与风险关联提前生成风险任务
任务到人
不只通知角色，而是分派到具体成员
自动整理
自动读取微信群日报目录，提取进展和材料
人工确认
智能生成内容必须经责任人确认
留痕追溯
提醒、草稿、确认、填报均可查询依据
技术路线（一句话）：流程可控的上报辅助系统，不是开放式自主智能体。前端采用独立 Web 工程，推荐 Vue 3 + TypeScript + Vite + Element Plus；后端是 Python API 服务，确定性业务流用 FastAPI + PostgreSQL；智能工作流用 LangGraph 编排，大模型只在节点内做“文本到结构化”的填空。耗时任务统一经 Celery 执行，技术栈选用 PostgreSQL、Redis、Celery、MinIO。

用户范围 · 轻量人员模型

用户类型主要职责
项目负责人查看总览、重大风险、逾期任务，确认关键结果
项目执行人补充现场日报资料、照片、进度说明，响应风险提醒
资料与填报负责人审核日报解析、整理附件、审核草稿、启动填报助手
实施管理员导入 WBS、风险源，配置成员、规则、模板和字段映射

一个人可承担多个职责，系统按责任标签分派任务。

MVP 必须做

  • 项目后台初始化 / 成员与责任配置
  • WBS 计划导入 / 风险源清单导入
  • WBS 工序与风险源人工关联
  • 风险预警任务生成
  • 微信日报目录监听 / 文件基础解析
  • 日报进展匹配 WBS / 风险材料缺项提醒
  • 风险进展上报草稿生成 / 人工审核确认
  • 网页填报助手原型 / 操作日志

MVP 暂不做

  • 不做完整项目管理平台
  • 不做所有平台接口打通
  • 不保存外部平台账号密码
  • 不绕过验证码、不自动最终提交
  • 不做复杂进度计划自动调整、节点自动顺延
  • 不做全量监测数据智能预警
  • 不做复杂图像识别闭环
  • 不做企业级跨项目看板

核心业务场景

  1. 后台初始化 WBS 与风险源　— 导入计划与清单、建立关联、配置提醒规则与材料要求
  2. 按 WBS 工序提前触发风险提醒　— 提醒转化为任务，分派到人，展示触发原因与所需材料
  3. 从微信群日报文件获取实际进展　— 定时扫描、去重、提取日期/进度/照片/问题
  4. 用日报实际进展校验 WBS 工序状态　— 高/低置信度/无法匹配分流，低置信度生成确认任务
  5. 生成风险进展上报草稿　— 标明数据来源与缺项，必须允许人工修改
  6. 网页平台辅助录入　— 用户自登录，助手填字段传附件，停在提交前

03

系统架构设计

上下文、逻辑架构、关键流程、状态机、安全边界、技术分层

架构总则 · A/B 双层

A 类 · 确定性业务流（约 70%）
项目/成员/责任配置、WBS 与风险导入、关联、提醒规则按日期计算、任务状态机、目录扫描去重、填报包组装。
规则 + SQL + 定时器，用 FastAPI + SQLAlchemy 直接实现，不碰图编排与大模型。
B 类 · 受控智能工作流（约 30%，价值核心）
日报解析（抽取→补抽取→语义匹配→挂起确认→回流）、风险草稿生成（聚合→生成→缺项→审核打回）、自然语言录入（预留）。
多步 + 分支 + 循环 + 中途暂停等人工确认，用 LangGraph 编排。
关键定位：LangGraph 只取其“状态机 + 人在环 interrupt + 持久化断点续跑”能力，当作确定性工作流引擎。节点和边由工程师写死，大模型只负责节点内的“文本 → 结构化”填空，不自主决定流程走向。Hermes 只作为 LangGraph 按需调用的复杂子任务工具，用于未知格式兜底、跨系统取数、复杂网页操作，不作为流程编排者。

逻辑分层

① 前端应用层
Vue 3 + TypeScript + Vite + Element Plus 独立工程；工地端首页、任务中心、风险页、日报确认页、草稿页、配置页、填报助手页
② 业务服务层（A）
认证权限、项目/成员、WBS、风险源、关联、任务、日报、草稿、填报包、日志 API
③ 智能工作流层（B）
日报解析工作流、风险草稿工作流、自然语言录入预留、统一 LLM 客户端、文件解析器、Hermes 复杂子任务工具
④ 异步任务与调度层
Celery Beat 定时（扫描/提醒/逾期）、Celery Worker 队列、Redis Broker/Backend、Playwright 填报助手
⑤ 数据层
PostgreSQL（业务态 + LangGraph Checkpoint）、Redis、MinIO 对象存储、微信日报目录

核心状态机

任务状态机

pending→ processing→ need_more_info↔ pending_confirm→ completed

日报解析状态机

discovered→ processing→ parsed / low_confidence→ pending_review→ confirmed→ archived

风险草稿状态机

draft→ pending_review↔ revised→ confirmed→ packaged

技术选型与分层（已定基线）

技术栈按职责分层选型：前端采用独立 Web 工程，不使用 Python 前端；推荐 Vue 3 + TypeScript + Vite + Element Plus。A 类确定性业务用 FastAPI + PostgreSQL，B 类智能工作流单独引入 LangGraph。基础设施统一为 PostgreSQL 15、Redis 7、Celery、MinIO。

层级选型说明
前端层Vue 3 + TypeScript + Vite + Element Plus独立前端工程，通过 JSON API 调用后端；负责路由、表格、表单、状态轮询、任务操作与审核交互
业务服务层（A）FastAPI + Pydantic业务 API、认证、权限、日志，纯确定性逻辑
业务数据层PostgreSQL 15存结构化业务态
对象存储MinIO存日报、照片、附件原件，元数据落附件表
缓存与队列Redis 7作 Celery Broker/Backend 与缓存
智能工作流（B）LangGraph + PG Checkpointer日报解析、草稿生成、自然语言录入预留三条工作流；状态机 + interrupt 人在环 + 断点续跑落 Postgres
大模型访问统一 LLM 客户端模型/超时/重试/降级集中；Pydantic 结构化输出；Prompt 与 schema 版本化
文件解析docx / xlsx / pptx / pdf按 MIME 分发的 Parser 接口（图片 OCR 可选）
复杂子任务工具Hermes被 LangGraph 按需调用，用于未知格式兜底、跨系统取数、复杂网页操作；不作为流程编排者
异步与调度Celery（Beat + Worker）定时跑扫描/提醒/逾期；耗时工作流投递到 Celery Worker
网页填报Playwright（受控）用户自登录，不存密码、不绕验证码、不自动提交，全程留日志
边界约定：① Hermes 只作为复杂子任务工具，不编排业务流程；② 不把 A 类业务流塞进 LangGraph（纯 CRUD 无分支价值）；③ 不自建工作流步骤表替代 LangGraph（执行态交给 Checkpointer）。

初步数据库设计

PostgreSQL · 核心表、字段、关系、状态枚举

设计基线约定

  • 主键统一：全库主键统一用 bigint（BIGSERIAL），避免 int4 与 int8 外键混用
  • 项目外键用 project_id：projects.id 是项目唯一主键；各子表关联项目的外键统一用 project_id，不再设置项目业务编码字段，也不再单独维护标段名称字段
  • project_members 一表承载成员与归属：含 user_id、project_id、member_role，并含 display_name、phone、status；member_role 只表示项目内粗粒度归属
  • 附件归一到 attachments：一张 attachments 表（接 MinIO）统一承担日报、照片、附件原件元数据
  • 身份/权限/参与/职责四轴正交：users 只存自然人账号（跨项目唯一一份）；users.role 管系统级权限；project_members 管参与了哪些项目；responsibility_tags + member_responsibilities 管项目内岗位责任与任务分派。四轴分表、互不耦合，不把项目属性塞进用户表
  • B 类工作流执行态交 LangGraph：节点进度、中间状态、断点交 PostgreSQL Checkpointer，人在环用 tasks + interrupt，不自建工作流步骤表
  • 异步作业统一由 Celery 执行：Celery Beat 负责定时触发，Celery Worker 负责耗时作业执行；async_jobs 表只作为前端可见的状态镜像
  • 自然语言录入作为预留工作流：本期只在 source_type/job_type 等字段中保留 nl_intake 取值，不纳入 MVP 必交付实现

API 接口规划

前后端 API 边界 · 按业务模块组织

设计原则

前端工程基线：前端采用独立 Web 工程，不使用 Python 前端。推荐 Vue 3 + TypeScript + Vite + Element Plus，配合 Vue Router、Pinia 和 Axios/OpenAPI Client 调用后端 FastAPI JSON 接口。
  • 接口按业务模块组织，不按页面硬编码
  • 所有项目级业务数据带 project_id 或从当前项目上下文获取
  • 智能生成内容必须有确认接口
  • 文件导入、日报解析、草稿生成、填报助手等耗时动作走异步作业
  • 外部平台密码、验证码不经本系统接口传输和保存
异步作业约定：触发接口返回 { job_id, status }，前端轮询 GET /api/async-jobs/{job_id} 查 status（queued / running / interrupted / succeeded / failed）。status 为 interrupted 时同时生成确认任务，用户在确认接口提交后工作流从断点恢复。

设计原则

  • 工地端首页以任务为中心，一线少看配置、多处理任务与确认
  • 每个页面都要明确下一步操作
  • 智能生成内容必须可编辑、可确认、可追溯
  • 风险、逾期、缺项要突出，但不制造信息噪音
  • 耗时操作走异步作业，页面以进度状态轮询展示，不阻塞用户
  • 网页填报助手必须明确安全边界：不保存密码、不绕验证码、不自动提交

开发任务拆解与排期建议

里程碑、任务拆解、依赖关系、交付顺序

里程碑总览

M0开发准备
样例、字段、规则、环境与技术选型确认
样例文件、字段字典、模板；确认前端工程基线、主键升 bigint、Celery、LLM 客户端、LangGraph+PG Checkpointer、Hermes 边界、Parser、Playwright 路线
M1基础底座
项目、成员、责任、日志、前端骨架
后台基础配置可用；搭建 frontend 独立前端工程骨架；搭建异步基础设施骨架（Celery Beat + Worker + Redis + async_jobs 表）
M2WBS 风险底图
WBS、风险源、人工关联
可生成风险预警依据
M3任务中心
风险提醒任务到人
工地端任务闭环可用
M4日报解析
目录扫描、文件解析、人工确认
LLM 客户端 + Parser；用 LangGraph 实现解析工作流（抽取→匹配→interrupt 确认→回流）
M5草稿生成
缺项检查、风险草稿、审核确认
用 LangGraph 实现草稿工作流（聚合→生成→缺项→审核打回）
M6填报助手原型
填报包、字段映射、辅助录入
基于 Playwright 受控填报；保存草稿并停在提交前

推荐开发顺序

项目/成员/责任/日志→ WBS 导入→ 风险源导入→ WBS-风险关联→ 风险提醒任务→ 任务中心→ 日报扫描→ 日报解析→ 日报确认→ 风险草稿→ 填报包预览→ 网页填报助手
不建议一开始就投入大量精力做网页填报助手，因为它依赖草稿、字段映射、附件和人工确认都先稳定。

仍需拍板的开放项

  • LLM 供应商与具体模型（影响统一客户端与成本）
  • 图片是否走 OCR、走哪个引擎
  • Playwright 进程模型：后端独立服务 vs 浏览器扩展，如何共享用户登录态（技术不确定性最高，建议单独预研）
  • 日报 ↔ WBS 语义匹配是否引入 pgvector
  • Hermes 在内网/离线环境能否运行其依赖的浏览器与 MCP
  • dedup_key 的拼接规则需与预警生成逻辑一并定死，建议“链路 ID + 类型 + 触发日历日”
