# 工程智管家 MVP 总体建设方案

> 文档状态：开发前期基线版
> 编制日期：2026-06-09
> 试点项目：合流污水一期复线工程（总管部分）FXZ1.2 标

---

## 1. 建设背景

项目一线已经同时使用公司平台、股份平台、业主平台、检测平台、小程序、在线表格和微信群。信息化系统增加后，现场管理人员并没有变轻松，反而出现了新的负担：

- 平台多，填报入口多。
- 同类信息重复录入。
- 微信群、日报、照片、监测资料、平台表单之间缺少联动。
- WBS 计划和风险源清单存在，但没有主动提醒和任务分派。
- 日报文件能通过微信监听服务下载，但仍需要人工阅读、整理、提取。
- 风险进展上报、节点变更、材料上传仍然依赖人工复制粘贴。
- 项目部希望少数几个人承担更多管理事务。

因此，工程智管家 MVP 的目标不是再造一个新平台，而是在现有平台和项目一线之间建立一个智能工作层。

---

## 2. 产品定位

工程智管家 MVP 定位为：

```text
面向项目一线的进度风险提醒与填报减负智能体。
```

它承担的是“信息整理、风险提醒、任务推进、草稿生成、辅助填报”的工作，不替代公司平台、股份平台、业主平台和检测平台。

### 2.1 核心价值

| 价值 | 说明 |
|---|---|
| 少填报 | 从 WBS、风险清单、日报、照片和附件中提取信息，减少重复录入 |
| 早提醒 | 根据 WBS 工序计划和风险源关联提前生成风险任务 |
| 任务到人 | 不只通知角色，而是分派到具体成员 |
| 自动整理 | 自动读取微信群日报目录，提取实际进展和材料 |
| 人工确认 | 智能生成内容必须经责任人确认 |
| 协助填平台 | 用户自主登录后，系统辅助录入字段和上传附件 |
| 留痕追溯 | 提醒、草稿、确认、填报过程均可查询依据 |

### 2.2 技术路线（一句话）

工程智管家是一个流程可控的上报辅助系统，不是开放式自主智能体。系统采用前后端分离：前端是独立 Web 工程，推荐 Vue 3 + TypeScript + Vite + Element Plus；后端是 Python API 服务，A 类确定性业务流（项目配置、WBS/风险导入、提醒计算、任务流转）用 FastAPI + PostgreSQL 直接实现；B 类智能工作流（日报解析、风险草稿生成、自然语言录入预留）用 LangGraph 编排，取其状态机、人在环暂停确认与断点续跑能力，大模型只在节点内做“文本到结构化”的填空，不自主决定流程。耗时解析与工作流统一经 Celery 执行（Beat 定时 + Worker 队列），技术栈选用 PostgreSQL、Redis、Celery、MinIO。

## 3. 建设目标

MVP 阶段围绕 FXZ1.2 标试点项目，优先实现以下目标：

1. 建立项目后台基础数据，包括项目、成员和责任标签。
2. 导入 WBS 施工进度计划，形成工序底图。
3. 导入风险源清单，形成风险源库。
4. 建立 WBS 工序与风险源的人工关联关系。
5. 根据 WBS 计划时间、风险等级和提醒规则生成风险预警任务。
6. 从微信群监听服务下载目录中读取日报文件。
7. 从日报文件中提取实际施工进展、照片、问题和风险相关内容。
8. 将日报进展与 WBS 工序进行匹配，低置信度结果进入人工确认。
9. 根据风险源、WBS、日报和附件生成风险进展上报草稿。
10. 根据材料要求检查缺项并生成补充任务。
11. 责任人审核草稿后生成平台填报包。
12. 用户自主登录目标平台后，由网页填报助手辅助录入和上传附件。
13. 系统保存草稿后停留在最终提交前，最终提交由用户本人完成。

---

## 4. MVP 业务闭环

```text
后台初始化
  -> WBS 计划导入
  -> 风险源清单导入
  -> WBS-风险源关联
  -> 风险提醒规则配置
  -> 风险预警任务生成
  -> 微信日报目录扫描
  -> 日报解析与确认
  -> WBS 状态匹配
  -> 材料缺项检查
  -> 风险草稿生成
  -> 人工审核确认
  -> 平台填报包
  -> 网页辅助填报
  -> 用户最终提交
```

这条闭环是 MVP 成功的核心判断标准。

## 5. 用户范围

MVP 不做复杂组织架构，采用轻量人员模型。

| 用户类型 | 主要职责 |
|---|---|
| 项目负责人 | 查看总览、重大风险、逾期任务，确认关键结果 |
| 项目执行人 | 补充现场日报资料、照片、进度说明，响应风险提醒 |
| 资料与填报负责人 | 审核日报解析、整理附件、审核草稿、启动填报助手 |
| 实施管理员 | 导入 WBS、风险源，配置成员、规则、模板和字段映射 |

一个人可以承担多个职责，系统按责任标签分派任务。

## 6. 系统边界

### 6.1 MVP 必须做

- 项目后台初始化。
- 成员与岗位责任配置。
- WBS 计划导入。
- 风险源清单导入。
- WBS 工序与风险源人工关联。
- 风险预警任务生成。
- 微信日报目录监听。
- 日报文件基础解析。
- 日报进展匹配 WBS 工序。
- 风险材料缺项提醒。
- 风险进展上报草稿生成。
- 人工审核确认。
- 网页填报助手原型。
- 操作日志。

### 6.2 MVP 暂不做

- 不做完整项目管理平台。
- 不做所有平台接口打通。
- 不保存外部平台账号密码。
- 不绕过验证码。
- 不自动最终提交平台流程。
- 不做复杂进度计划自动调整。
- 不做重大节点自动顺延。
- 不做全量监测数据智能预警。
- 不做复杂图像识别闭环。
- 不做企业级跨项目看板。

## 7. 阶段规划

| 阶段 | 目标 | 主要成果 |
|---|---|---|
| 开发准备 | 确认样例、字段、模板和规则 | 样例文件、字段映射、任务清单 |
| 基础底座 | 项目、成员、责任、日志 | 后台配置能力 |
| 风险底图 | WBS、风险源、关联规则 | 风险预警可计算 |
| 任务闭环 | 风险提醒任务到人 | 工地端任务中心 |
| 日报闭环 | 目录扫描、解析、确认 | 实际进展可复用 |
| 草稿闭环 | 缺项检查、草稿生成、审核 | 风险上报草稿可用 |
| 填报原型 | 填报包、字段映射、网页辅助 | 保存草稿并提交前暂停 |
| 开发收口 | 用样例数据跑通主闭环 | 可演示版本和问题清单 |

---

## 8. 开发完成判断

MVP 开发收口时，应能用样例或试点数据完成以下演示：

1. 导入一份 WBS 计划并形成工序库。
2. 导入一份风险源清单并形成风险源库。
3. 人工配置至少一批 WBS-风险源关联。
4. 系统根据计划时间生成风险预警任务。
5. 任务能分派到具体责任人并完成状态流转。
6. 系统能扫描微信群日报目录并解析新增文件。
7. 责任人能确认日报解析结果。
8. 系统能基于风险源、WBS、日报和附件生成风险进展草稿。
9. 草稿能人工修改、确认并生成填报包。
10. 网页填报助手能在用户自主登录后辅助录入并保存平台草稿。
11. 关键过程有日志，关键结论有来源。
