# 任务引擎功能手册

面向使用与测试。所有示例均已在本机实测通过。

---

## 一、它解决什么问题

多数项目管理系统能存任务、能改状态，但**「到点自动布置任务」这件事往往是缺失的**。界面上让用户配了"每周五执行"，提交时这个配置却被拼成一句话存进备注字段，没有任何调度器会读它——用户以为设好了定时，实际永远不会触发。

这个引擎补的就是这一段，并把流转、留痕、逾期判定一起做成了产品无关的通用能力。

**一句话**：把「每周五检查基坑监测数据」这样一句话，变成一个会自动派发、按顺序流转、全程留痕的任务流。

## 二、五分钟上手

在 Claude Code 里直接用自然语言，不需要记工具名。

### 第 1 步：说出你的需求

> 每周五检查基坑监测数据，接近预警值时由监测员复核，项目负责人确认后归档

引擎会返回一个任务流（实测结果）：

```
标题：检查基坑监测数据
触发：2026-08-14 09:00 首次执行，之后每 1 周执行一次
节点：
  1. 执行巡检      → 巡检记录与照片  ⚠必须留证
  2. 数据汇总分析  → 分析结论
  3. 异常上报处理  → 处理意见
  4. 巡检归档      → 巡检报告
```

注意它把「每周五」正确解析成了 **8月14日**（确实是星期五），而不是简单地"从今天起每7天"。

### 第 2 步：登记定时计划

> 帮我登记这个任务流的定时计划

**这一步很关键**——生成任务流只是画好了流程图，登记计划才让它到点自动派发。

### 第 3 步：让它跑起来

> 假设现在是 8 月 14 日早上 9 点，推进一下引擎

```
触发 1 个任务
```

再推进一次同样的时刻：

```
触发 0 个任务   ← 幂等，不会重复派发
```

### 第 4 步：办理

> 我有哪些待办任务？
>
> 完成第一个节点，附件是 现场照片.jpg
>
> 第二个节点我干不了，转给李四

## 三、核心概念

理解这四个概念，就理解了整个引擎。

| 概念 | 是什么 | 类比 |
|---|---|---|
| **任务流 (flow)** | 可复用的流程模板 | 一张流程图 |
| **触发计划 (schedule)** | 流程图 + 时间 | 挂在墙上的日程表 |
| **任务 (task)** | 流程的一次具体执行 | 这周实际要干的活 |
| **节点 (step)** | 任务里的一个环节 | 流程图上的一个框 |

**关系**：一个任务流可以被触发很多次，每次产生一个独立的任务。改流程图不影响已经派出去的活。

### 状态

**任务状态**

```
待开始 → 进行中 → 待验收 → 已完成
           ↓
        受阻 / 已逾期 / 已取消
```

**节点状态**：未开始 → 进行中 → 已完成（旁支：已跳过、受阻）

任务状态由节点状态自动推导，不需要你手动同步。

## 四、两条铁律

这两条是引擎刻意强制的，测试时可以专门验证。

### 铁律一：必须按顺序办理

不能越过前面的节点直接完成靠后的。实测：

> 直接完成第 4 个节点

```
当前应处理节点「执行巡检」（第 1 个），不能跨越到「巡检归档」
```

**为什么**：否则就是"没整改先归档"，任务流的顺序约束形同虚设。

### 铁律二：要求留证的节点必须传附件

实测：

> 完成第一个节点，说明"已巡检"

```
节点「执行巡检」要求提交证明材料
```

**为什么**：涉及现场作业、整改、验收的环节，工程规范要求有材料留痕。

## 五、责任人规则

这块容易混淆，单独说明。

| 节点状态 | 能否改派 | 场景 |
|---|---|---|
| 已完成 / 已跳过 | ❌ | 历史责任归属不可篡改 |
| 当前流转中 | ✅ | **转办**——我干不了，换人接手 |
| 尚未轮到 | ✅ | **排班**——提前安排后续人手 |

**关键区别**：改派只决定"轮到这一步时谁来干"，**不会让那个人现在就能干活**。老李被提前指派到第 4 步，他依然得等前三步都完成才能动手——因为完成节点受铁律一约束。

**「我的任务」的语义**：查某人的任务，返回的是"他当前负责的活"。节点完成后，任务会自动从上一个人的列表消失，出现在下一个人的列表里。

## 六、定时触发详解

### 支持的表述

引擎能从中文里直接解析出周期规则：

| 你说 | 解析结果 |
|---|---|
| 每周五… | 每周，首次落在最近的那个周五 |
| 每 3 天… / 每三天… | 每 3 天 |
| 每两周… | 每 2 周 |
| 每月… / 每个月… | 每月 |
| 每 2 小时… | 每 2 小时 |
| 定期… / 周期性… | 默认每周 |
| （没有周期词） | 一次性任务 |

### tick：引擎的心跳

引擎**不常驻**，靠外部定期调用 `tick` 驱动。每次 tick 做两件事：

1. 触发所有到期的计划 → 创建任务
2. 扫描所有超期未闭环的任务 → 标记逾期

**测试时**可以传入指定时刻，模拟"如果现在是下周五"，不用真等：

> 假设现在是 2026 年 8 月 21 日，推进引擎

**真实部署**要挂 cron：

```bash
*/5 * * * * cd /Volumes/Media1/Code/Task && PYTHONPATH=src /usr/local/bin/python3.13 -m task_engine.cli tick
```

`tick` 是幂等的，调用频率高于触发间隔也不会重复派发任务。

### 三个已验证的边界

**月末不漂移**：1月31日起按月重复，得到的是 01-31、02-28、**03-31**、04-30、**05-31**。2 月被夹到 28 日后能回弹到 31 日，而不是一路滑成 28 日。

**停机不补跑**：停机 5 周后重启，只触发一次然后跳到未来，不会把错过的 5 次全部补发出来。

**高频调用安全**：模拟每 5 分钟 tick、连续 3 天（864 次），恰好触发 3 次。

## 七、内置模板

不想描述需求时，可以直接选模板。

| 模板 | 节点数 | 流程 |
|---|---|---|
| **隐患整改** | 5 | 发现隐患 → 派单整改 → 整改报验 → 安全员复核 → 闭环归档 |
| **条件核查** | 4 | 发起核查 → 现场复核 → 负责人确认 → 核查归档 |
| **资料补全** | 4 | 识别缺失项 → 补齐资料 → 资料复核 → 归档入库 |
| **风险处置** | 5 | 风险触发确认 → 数据复核 → 制定措施 → 处置执行 → 风险关闭 |
| **报告审核** | 4 | 提交报告 → 依据审核 → 问题修订 → 审核通过 |

## 九、测试剧本

按这个顺序走一遍，能覆盖所有关键能力。

### A. 基础流程

```
1. 每周五检查基坑监测数据，异常时由监测员复核，负责人确认后归档
2. 登记这个任务流的定时计划
3. 假设现在是首次触发那天，推进引擎        → 触发 1 个
4. 再推进一次同样的时刻                    → 触发 0 个（幂等）
5. 我有哪些待办任务？
```

### B. 验证约束（故意犯错）

```
6. 直接完成最后一个节点                    → 应拒绝：不能跨越
7. 完成第一个节点，不传附件                → 应拒绝：要求证明材料
8. 完成第一个节点，附件是 现场照片.jpg     → 成功
9. 还没做完就验收                          → 应拒绝：只有待验收能通过
```

### C. 多人协作

```
10. 用隐患整改模板建流程，指派张三、李四、王五
11. 立即布置
12. 张三有哪些任务？                       → 1 个
13. 李四有哪些任务？                       → 0 个
14. 把当前节点转给王五
15. 张三还有任务吗？                       → 0 个
16. 王五呢？                               → 1 个
```

### D. 异常处理

```
17. 把当前节点标记为受阻，原因是等材料进场
18. 查看任务状态                           → 受阻
19. 解除阻塞
20. 查看任务状态                           → 进行中
```

### E. 验收与退回

```
21. 逐个完成所有节点（要留证的记得传附件）
22. 查看状态                               → 待验收
23. 退回，理由是数据来源不明
24. 查看状态                               → 进行中，最后一个节点重新打开
25. 重做完成后验收通过                     → 已完成
26. 查看完整历史                           → 每一步都有留痕
```

### F. 逾期

```
27. 假设现在是三个月后，推进引擎           → 未完成的任务被标记逾期
```

### G. 长期节奏

```
28. 建一个每月执行的计划，首次 1月31日
29. 依次推进到 2月28日、3月31日、4月30日
    → 验证 3 月能回到 31 日，没有漂移
```

## 十、配置

`.mcp.json` 里的 `env` 段：

| 变量 | 默认值 | 说明 |
|---|---|---|
| `TASK_ENGINE_DB` | `task_engine.db` | 数据库路径 |
| `TASK_ENGINE_TZ` | `Asia/Shanghai` | 时区 |
| `TASK_ENGINE_AI_KEY` | 空 | **留空则用规则生成** |
| `TASK_ENGINE_AI_BASE_URL` | OpenAI 官方 | 兼容接口地址 |
| `TASK_ENGINE_AI_MODEL` | `gpt-4o-mini` | 模型名 |

### 关于模型

**现在没配模型，走的是规则解析**——常见的中文周期表述都能识别，够用。

配了模型之后，节点拆分和人员指派会更贴合具体需求（不再局限于 7 个固定模板）。走 OpenAI 兼容接口，OpenAI / 通义 / DeepSeek / 本地 vLLM 都只需改 `BASE_URL` 和 `MODEL`。

**模型不可用绝不阻断你**：没配 key、超时、返回脏数据，都会静默降级到规则生成，你拿到的始终是可编辑的合理流程，只是结果里的 `origin` 字段会如实标明来源（`ai` 还是 `rules`）。

## 十一、常见问题

**Q：生成了任务流，为什么「我的任务」里没有？**
生成只是画好流程图。要么 `dispatch_task` 立即布置，要么 `create_schedule` 登记定时。

**Q：登记了定时计划，为什么到点没触发？**
引擎不常驻，需要外部调用 `tick`。测试时手动让它推进，真实部署要挂 cron。

**Q：想重新开始测试？**
删掉 `task_engine.db` 即可（重启 Claude Code 后生效）。

**Q：改了任务流，已经派出去的任务会变吗？**
不会。任务是流程的快照，改模板只影响之后新触发的任务。

**Q：怎么知道生成结果是模型还是规则？**
看返回的 `origin` 字段：`ai` / `rules` / `template`。`origin_note` 里还会说明具体原因。

## 十二、命令行

不经 Claude Code 也能用，适合脚本化和排查问题。

```bash
cd /Volumes/Media1/Code/Task
export PYTHONPATH=src
P() { .venv/bin/python -m task_engine.cli "$@"; }

P generate "每周五检查基坑监测数据"     # 生成
P templates                             # 列模板
P flows                                 # 列任务流
P schedule <flow_id> --at "2026-08-14 09:00" --mode recurring --every 1 --unit week
P tick --now "2026-08-14 09:00"        # 推进（可指定时刻）
P tasks --assignee u1                   # 我的任务
P task <task_id>                        # 详情
P complete <task_id> 0 --attach x.jpg   # 完成节点
P forward <task_id> 1 u2 --name 李四    # 改派
P accept <task_id>                      # 验收

P --json tasks                          # 输出原始 JSON
```
