# 长期记忆与学习统一控制方案

日期：2026-09-10。状态：历史设计与实施记录。第 1—13 节为实施前讨论，第 14—15 节为前两阶段记录；其中人工读写分配、逐智能体开关与三选项均已被第 16 节的最新授权方案取代，不再作为当前配置建议。现行规则以[记忆与学习职责与运行规则](../操作说明/记忆与学习职责与运行规则.md)为准。

## 1. 结论

保留每个智能体的三个记忆范围及读写配置，删除“管理层／执行层”的隐含资格限制。记忆归属于用户或项目，智能体是使用者与素材提供者，后台学习由系统统一处理。

调用关系、直接能力、数据权限、业务确认和后台学习分别有唯一的规则来源。通过协作可以组合能力，但不能扩大用户、项目、资料选择和消息受众的范围。一次协作的记忆写入与学习按完整业务过程处理，避免多个智能体重复保存或相互把输出当成事实。

本轮不增加“记忆助手”“学习主智能体”或第四个企业记忆抽屉，也不增加另一套与现有界面重复的配置。

## 3. 各类控制各管一件事

| 规则 | 决定什么 | 不承担什么 |
| --- | --- | --- |
| 主智能体固定职责 | 谁负责首页、初始化、资料问答、任务生成 | 不决定用户能看哪些项目数据 |
| 公开／内部、启用、发布 | 用户入口与业务智能体可用性 | 不决定长期记忆权限 |
| 接收许可与调用方协作名单 | A 是否可以委派 B | 不授予 B 的工具给 A |
| 智能体能力配置 | 该智能体直接使用的 MCP、技能、数据库能力及记忆范围 | 不替代用户或项目授权 |
| 当前业务运行权限 | 谁提出请求、哪个项目、什么场景、哪些人能看到结果、可使用哪些来源 | 不由智能体提示词改写 |
| 系统学习策略 | 哪些来源进入学习、何时处理、如何校验和失效 | 不依赖总控是否回复、是否开启其个人学习参与开关 |

总控是业务编排主体，不是超级账号；项目管理员在多人场景下，也不能把自己的私人记忆自动展示给其他成员。

## 4. 固定调用边界

| 智能体 | 用户直接入口 | 接受其他智能体调用 | 向外协作 |
| --- | --- | --- | --- |
| 总控 | 首页 Dobby | 永不接受 | 任务助手、知识库助手，以及已启用且允许总控调用的业务智能体 |
| 项目初始化 | 初始化页面 | 永不接受，包括总控 | 按已保存名单调用专家或其他允许的协作对象 |
| 知识库助手 | 工程资料问答 | 固定允许总控；其他调用方须满足邀请许可和名单 | 按已保存名单 |
| 任务助手 | 任务生成；现有群聊 `@任务助手` 的任务草稿场景 | 固定允许总控；其他调用方须满足邀请许可和名单 | 按已保存名单 |
| 公开业务智能体 | 启用并发布后进入业务列表及 `@` 候选 | 总控许可与其他邀请许可分别检查 | 按已保存名单 |
| 内部业务智能体 | 无用户直接入口，不进入普通业务列表和 `@` 候选 | 按相应接收许可 | 按已保存名单 |

主智能体不能停用。任务助手的固定群聊入口是任务业务入口，不是把所有内部业务智能体开放给用户。上述调用关系本轮不作新的权限扩张。

每条调用边单独验证，不提供传递授权：A 能调用 B、B 能调用 C，不代表 A 可以直接调用 C。A→B→C 可以按业务需要执行，但整条链必须受同一业务运行边界约束。C 返回 B、B 返回 A 属于结果回传，不是重新邀请上级。禁止 A→B→A 等运行内循环。

## 5. 记忆归属与内容边界

三个抽屉继续保留：

| 范围 | 适合保存 | 典型读取方式 |
| --- | --- | --- |
| 用户级 | 本人明确的跨项目称呼、表达偏好、个人工作习惯 | 本人的私聊；本人换项目后仍可使用 |
| 用户＋项目级 | 本人在当前项目的偏好、私人工作记录、仅对本人可见的项目经验 | 本人在该项目的私聊 |
| 项目级 | 全项目可见的、带来源的约定和可复用经验 | 当前项目获授权的业务场景 |

记忆不按智能体复制一份。用户在知识库助手处更正称呼后，总控可在同一身份、同一范围和读取许可下使用。来源智能体用于追溯，不成为记忆所有人。

只有真正跨项目的个人信息才进入用户级；带项目或受限资料来源的内容不能转存用户级来绕过项目撤权。群聊中明确的个人偏好只归属于真实发言的本人，不能因另一成员或智能体的转述修改别人的偏好，也不从称呼推导岗位或账号权限。

工程任务状态、人员名单、工期等实时事实以业务数据库为准；合同、规范及项目文件依据以当前授权资料为准。记忆保存引用、偏好、方法与历史结论，不用记忆中的旧值覆盖业务事实。

后台生成的经验和操作步骤继续是记忆内容；管理员分配的“技能”是受管理的能力说明。学习不会自动安装 MCP、修改提示词、分配技能、扩大协作名单或训练模型参数。

## 6. 一次业务运行的权限如何传递

### 6.1 统一运行身份

所有入口由业务后端登记真实运行身份，至少包括组织、请求用户、项目、入口类型、根运行、调用链、输出受众、资料选择、来源证据和是否允许学习。聊天记录、任务草稿、初始化草稿是可以关联的业务对象，不要求所有入口伪装成普通聊天。

任务编辑器也必须有能被网关验证的运行绑定，不能仅传一段含用户／项目 ID 的文本。调用中的智能体不能更改身份、根项目、输出受众或学习禁用标记。

### 6.2 能力可以组合，数据访问不能扩大

当前智能体的有效读取范围，由其直接读取配置、当前用户权限、运行场景和来源可见性共同决定。被调用方按自己的直接能力配置工作，不照抄调用方工具名单。

例如总控没有直接知识库工具，但可以让知识库助手查询当前用户被授权且属于本次资料范围的内容，再返回带来源的答案。这是正常组合能力。业务智能体读取了自己的工具结果，也不能借另一智能体去扩大项目或文档范围。

“当前智能体不直接读取某个抽屉”与“本次任务禁止使用该抽屉”要区分：前者是该智能体的直接能力配置，后者是用户或场景的运行约束。运行约束必须传到所有子任务，不能通过委派规避。常规页面不新增一个权限模式切换器。

### 6.3 输出受众比发起人身份更重要

- 本人私聊：按本人权限查询个人及项目记忆。
- 多人群聊：不注入任何个人、个人＋项目抽屉，包括发起 `@` 者的个人记忆。
- 多人回答中用到的项目资料或来源受限经验，必须对输出受众可见；不能只验证发起人能看。
- 只在受限子群可见的材料，不因调用知识库助手、总控转述或群后来扩员而变成全项目记忆。
- 资料页面限定文件／目录时，知识库助手的子调用、结果和可召回资料引用同样受这个选择约束。
- 在同一次运行中改变项目、发布目标或群成员范围，重新检查来源；不把原权限快照当作长期授权。

依赖受限资料生成的总结、任务草稿和学习成果都保留来源限制。无法证明可以共享时，保留较窄范围；不能仅靠模型删除几处姓名就认为可以扩大受众。

## 7. 直接保存与后台学习分开处理

### 7.1 用户明确要求记住

如“以后称呼我王工”“这个项目周报按问题、责任人、期限排列”，当前入口智能体可以提交保存请求。系统检查真实用户来源、读写范围、内容归属和当前版本后保存，成功才告知“已记住”，不额外排一次学习模型调用。

写权限仍然有实际作用。它限制当前智能体可发起的新增、修改和删除范围；业务事实修改继续走业务接口。删除或修改已有记忆必须指向具体版本，不把“能写记忆”理解为能清空共享抽屉。

### 7.2 协作过程只提交一次记忆变更

主张按一次根业务运行提交记忆变更：各节点通过受控工具直接向后端提交结构化候选、原始证据引用和目标范围，后端统一处理；被调用节点不能绕过该入口直接改动正式记忆。候选持久化属于待处理材料，不等于已经生效的长期记忆。

直接面对用户的入口是本次业务的归属和权限依据，负责业务答复与呈现真实保存回执；不要求它逐层转述候选、重新组织证据或决定程序何时落库。后台以原始证据和运行状态处理，即使入口没有把某个候选写进最终回答，也不能据此丢失该候选或来源约束。

候选的范围同时受来源智能体写权限、入口智能体写权限、用户权限和来源范围约束。来源智能体写权限关闭时，不能让上级把其候选机械转存；入口写权限关闭时，也不能让子智能体替它落库。后来用户明确确认一条新事实，是新的用户事件，重新按权限处理。

总控→任务助手→专业智能体的同一结论只提交一次；任务助手被用户直接打开时，它自己就是入口，不必经过总控。

### 7.3 两类学习来源统一处理

| 来源 | 控制策略 | 生效条件 |
| --- | --- | --- |
| 智能体业务交互与协作过程 | 系统总开关、当前根运行约束、入口及贡献智能体的学习参与设置 | 原始用户纠正、真实工具结果等足以支持候选内容；最终写入不超过相关智能体写范围 |
| 群聊消息、初始化确认、任务发布／验收等业务事件 | 系统来源策略及业务事件自身权限 | 来源真实且有效、可见范围确定、业务阶段与结论匹配 |

第二类来源不借用总控账号或总控的读写勾选。群聊无需 `@` 就能按系统机制处理；任务和初始化的确认事件也不应因换了负责执行的智能体而失去记录。

两类路径汇入现有学习服务，按业务运行、原始证据 ID 和版本归并。同一任务的群消息和智能体转述如果引用相同证据，只形成一份素材及相应候选；不把转述当成多次独立成功。

关闭某个智能体的参与开关，阻止其交互材料进入新的学习；不能把其材料复制到总控回复中绕过。独立存在的真实用户消息或正式业务事件仍按系统来源策略处理。用户明确要求“这段不要记忆或学习”时，在来源和整个调用链标记排除，系统来源处理也遵守。

### 7.4 业务阶段决定能学到什么

- 生成有效任务草稿，只能证明“生成了结构有效的草稿”；不能证明任务已发布、现场工作完成或方法有效。
- 用户确认任务流程，可以提炼被采用的编排方式；执行和验收事件才能提供实际结果证据。
- 初始化草稿未确认前不能变成已确认项目事实。正式应用成功后，可以从已确认修订和版本中提炼方法；正式字段仍从数据库读取。
- 知识库问答可积累检索路径、回答格式、带来源的纠正；不默认把整段资料复制到长期记忆，更不扩大受众。
- 单独工具失败不形成“成功经验”。失败后经实际验证的修复才可提炼为带适用条件的方法。
- 停止、失败、被用户拒绝的草稿不能形成业务成功证据；如有真实故障修复证据，可作为另一种明确标记的来源。

### 7.5 自动生效与失效

系统先提炼候选，再核对证据 ID／版本、来源权限、内容类型、适用条件和限制，通过后按当前产品方向自动生效。证据不足可为空结果或保持不可用，不强制每天生成经验，也不要求用户逐条审批正常学习成果。

模型负责语义判断，程序负责权限、来源和结构等确定性检查；这不能保证结论永远正确。与正式数据冲突、只有助手自评或不能支持结论的材料不能自动写成确定事实。

撤回、删除、来源修订、退群、项目授权收回后，停止召回受影响的内容并更新依赖结果。失效处理不消耗学习预算，也不因暂停新学习而停掉。群成员扩大不自动开放旧的受限来源。

已经生效的合法共享记忆属于用户或项目，不因来源智能体被删除、改名或关闭新学习而消失。暂停新学习、停用已有成果、删除记忆是三种不同操作。

## 8. 各场景的推荐行为

| 场景 | 读取 | 保存／学习 |
| --- | --- | --- |
| 首页与总控私聊 | 本人偏好、当前项目记忆；实时数据另查 | 明确记忆可保存；有证据的纠正或结果进入学习 |
| 总控委派多个智能体 | 各节点按自己的能力及同一运行边界读取 | 各节点向后端提交证据／候选，后端按根运行归并；不各存一份 |
| 知识库页面问答 | 本人偏好、适用经验；资料答案遵守所选资料范围 | 保存沟通偏好；检索改进等有依据才学习 |
| 任务页面生成 | 当前用户／项目偏好、有效编排经验 | 未确认草稿不作正式事实；确认与验收由对应业务事件提供证据 |
| 群聊 `@任务助手` 或公开业务智能体 | 群受众可见的项目内容，不用个人记忆 | 草稿不等于发布；群聊来源与任务事件去重 |
| 无 `@` 的项目全体群 | 不启动对话智能体，系统增量采集 | 有价值的共同事实可进项目范围；自动校验，不逐条审批 |
| 受限子群 | 不注入个人抽屉；群内原始上下文按群权限提供 | 延续当前来源受限的成员用户＋项目归属，保留来源群权限，不升级到项目共享 |
| 初始化页面及专家协作 | 上传资料和草稿为主要依据；获授权的项目经验仅供参考 | 专家不各自写入正式事实；确认应用事件可供系统学习 |
| 用户直接使用公开业务智能体 | 与职责相符的授权记忆 | 该智能体作为根入口，遵循同一保存与学习规则 |
| 内部专家被调用 | 默认使用传入任务材料；需要时管理员明确开放记忆范围 | 默认不直接保存或贡献学习，业务确认事件仍由系统处理 |
| 管理中心调试 | 固定配置被忠实展示；使用隔离的测试身份和测试记忆 | 与业务记忆隔离，默认不进入正式学习；不得用管理员身份模拟普通用户绕过权限 |
| 权限撤销、取消、超时或服务故障 | 权限无法验证时不能使用受限记忆；普通对话按可用上下文继续 | 不误报保存成功；禁止取消后迟到的结果提交，重试保持幂等 |

调试用测试数据验证相同规则。若后续确需用真实项目做受控验证，应走显式绑定的业务身份和受众，仍不得把调试结果自动写入正式记忆。

## 9. 管理端保留哪些配置

### 9.1 智能体外部「记忆与学习」Tab

继续保留且只在这里配置，编辑弹窗不重复。

第一部分：三个范围的“读取／写入”表格。说明：

> 控制当前智能体直接使用记忆及提出记忆变更的范围。实际访问还受用户、项目、当前场景和来源权限限制；协作中的变更由后端按本次业务运行统一处理。

第二部分：两项上下排列的开关，各有独立说明：

| 开关 | 专属说明 |
| --- | --- |
| 允许系统从此智能体的业务交互中学习 | 系统可将本智能体参与的用户纠正和实际执行结果整理为记忆与经验，写入不超过已授权范围。与其他智能体协作时统一处理，关闭后不从其交互材料产生新学习。 |
| 允许使用已生效的学习经验 | 在读取权限内参考系统已校验的经验和操作步骤。关闭后仍可使用获授权的普通事实与偏好，不加载学习经验。 |

当前“记录素材／提炼素材”合并成第一个开关。保留运行日志和业务审计不等于授权学习，后台排队与故障重试由系统负责。

如果所有写范围都关闭，交互学习不能落库，界面直接提示这个依赖；不允许出现勾选正常但被隐藏层级禁用的情况。如果所有读范围关闭，则不能使用学习经验。不开新的折叠区或权限模式选择器。

### 9.2 系统「记忆配置」

集中设置后台学习总开关、各来源开关、学习模型和运行策略。来源区分智能体业务交互、群聊持续学习、已确认业务事件。模型为显式的系统配置，不能再隐式跟随总控或某次对话改变。

日常使用提供稳定默认值；处理频率、输入预算、重试等由系统管理，不下放到每个智能体。本轮不把尚未梳理的旧融合、压缩、Dreamer 参数再搬到新表单；逐项核对真实调用后删除失效配置。对话压缩属于会话运行机制，与长期学习分开说明。

全局暂停新学习不关闭已有记忆检索、不阻止用户明确保存／删除、不停止权限与来源失效检查。用户不需要在每个智能体里重复操作总开关。

### 9.3 默认策略是起点，不是新的层级

| 新建／明确重设时的对象 | 默认读取 | 默认写入 | 从交互学习 | 使用经验 |
| --- | --- | --- | --- | --- |
| 总控 | 三个范围 | 三个范围，实际项目写仍需业务授权 | 开启 | 开启 |
| 知识库助手、任务助手 | 三个范围 | 用户、用户＋项目 | 开启 | 开启 |
| 项目初始化 | 当前项目 | 关闭 | 关闭 | 开启 |
| 公开业务智能体 | 三个范围 | 用户、用户＋项目 | 开启 | 开启 |
| 内部业务智能体 | 关闭，按需要明确开放 | 关闭 | 关闭 | 关闭 |

初始化与任务的正式确认／验收由系统业务事件提供学习来源，因此不需要为专家打开项目记忆写权限。公开／内部切换只改可见范围，不自动套用默认值、覆盖既有权限。使用范围也不成为记忆资格判断条件。

这是建议的初始配置，不直接批量应用到当前数据。旧 worker 上勾选的“全范围”过去可能从未生效，删除层级门槛前必须给出现有每个智能体的有效权限与拟采用权限对照，避免静默放权。

## 10. 落地顺序

1. **明确并记录规则。** 本稿定稿后更新现行分工及记忆文档，将历史方案标明为历史，避免多个相互矛盾的说明同时充当依据。
2. **先补统一运行身份和数据边界。** 覆盖首页、知识库、初始化、任务编辑器、群聊、直接业务入口和委派；补充受众、资料选择与来源追溯，不只检查用户／项目 ID。
3. **建立一次运行的保存与学习归并。** 真实用户消息、委派任务、引用材料、工具结果、业务确认分别标记；接入初始化确认和任务生命周期事件，禁止把委派提示当作用户纠正。
4. **学习策略与总控解耦。** 系统来源拥有自己的策略和明确模型；原有学习服务承接统一事件，保留有效的幂等、来源校验、索引与失效能力。
5. **删除旧层级及重复开关。** 同时更新数据模型、权限检查、工具挂载、中间件、目录 DTO、管理端、初始化配置脚本与测试；两项旧学习参与字段换成一项明确字段。
6. **显式处理当前开发数据。** 先导出配置对照和可恢复快照，逐个确定有效权限，执行一次性数据更新。运行代码只接受新契约，错误状态显式暴露，不加入旧字段回退或启动时猜测迁移；不清空业务数据来简化工作。
7. **真实入口联调后交付。** 自动化测试验证规则，真实两端验证配置、身份与业务路径；不会用静态假页面代替真实页面。验证不得向真实群聊发布消息或实际布置任务来制造成功结果。

## 11. 验收清单

| 验收项 | 必须得到的结果 |
| --- | --- |
| 关闭总控交互学习 | 群聊持续学习不受影响；总控及其该次协作材料不被别的节点转存学习 |
| 无层级、业务智能体显式有读权限 | 真正能读到授权记忆；没有隐藏 worker 门槛 |
| 无读权限、无写权限、仅读、仅读普通事实 | 直接工具、自动注入、后台写入与界面分别符合配置 |
| 总控→任务助手→业务智能体 | 同一身份与受众、原始证据可追踪、统一保存、无重复学习 |
| 业务智能体→知识库助手 | 正常组合能力；直接知识库工具仍只属于知识库助手 |
| 业务智能体→总控或初始化；运行内循环 | 服务端拒绝；历史名单与已有子会话不能绕过 |
| 任务编辑器独立生成 | 网关能验证真实身份；使用有效偏好；只产生草稿 |
| 群聊明确 `@任务助手` | 不读取发起人的个人记忆；生成草稿，不擅自发布任务 |
| 同一用户切换项目／不同用户相同问题 | 个人范围按归属生效，项目内容不串用 |
| 管理员在群聊发起请求 | 管理员私有数据不因管理员身份暴露给群成员 |
| 受限资料产生答案／草稿／经验 | 所有派生成果继承来源约束，不能经转述洗掉权限 |
| 子群变全体群、成员加入退出 | 不扩大旧证据受众；失去权限者不能继续召回 |
| 用户要求本次不记忆不学习 | 整条委派链及系统来源都尊重排除标记 |
| 多次转述同一工具结果 | 不是多份独立证据，不重复累计成功次数 |
| 任务生成、确认、发布、验收 | 分清业务阶段；草稿成功不能学成现场任务成功 |
| 初始化未确认／确认应用 | 未确认内容不成为正式项目事实；确认事件可提供系统学习证据 |
| 用户纠正、来源修订、删除、撤权 | 更新、失效和版本检查贯通；旧结论不持续召回 |
| 关闭学习或耗尽当日预算 | 新学习暂停；已有有效记忆可用，失效检查继续 |
| 更换模型、关闭来源智能体 | 不重新学习全部历史，不删除合法有效的共享成果 |
| 调试与真实业务 | 配置语义相同、数据隔离；测试素材不污染业务记忆 |
| 失败、取消、并发与重试 | 不误报成功、不晚到写入、不覆盖新版本、不重复保存 |

## 12. 本方案的取舍

不采用“所有智能体独立全开学习”，因为当前多智能体调用会放大重复、误把转述当证据的问题；也不采用“只让总控有记忆”，因为用户可以从知识库、任务和公开业务智能体直接进入。

保留读写配置，用统一运行和证据归并控制协作；系统学习与总控解耦，用来源权限限制共享。用户需要管理的是职责、能力和记忆范围，系统负责身份、去重、校验、后台调度和失效。这是本项目下一轮应收敛到的一套规则。

## 13. 第二次代码复核：可行性与必要修正

结论：现有架构支持本方向，但不能仅调整开关、增加提示词或使用 `session_role` 就完成改造。采用“各节点向后端提交带来源的候选，后端统一处理”的实现，不依赖入口模型逐层转述和代存。

### 13.1 可沿用的基础

- `storage/_model/_session.py:59` 与 `_tool/_agent_invite.py:437` 已有入口／被委派标记及根会话；团队成员保存 `inviter_session_id`，用于还原直接上级。角色按本次会话确定，不是旧智能体层级。
- `_router/_session.py:334`、`:583` 限制平台归属由服务身份提供，普通管理账号不能伪造平台用户上下文。新权限解析仍须验证服务端实际会话和团队关系，不能只信一个角色字符串。
- `_team_lifecycle.py` 已有工作阶段版本、待处理成员、完成、失败和中断状态，可用于判断业务处理进度。
- `memory_repository.py` 已有权限、事务、幂等请求、抽屉锁、版本检查和索引任务；学习仓库已有租约与内容指纹；群聊已有来源消息版本和受众校验。

### 13.2 尚缺失的关键能力

| 缺口 | 代码核对 | 必须采取的处理 |
| --- | --- | --- |
| 根会话不是一次业务的唯一标识 | 根会话跨多轮使用，学习事件键包含节点会话和 `agent_id` | 明确业务运行及证据版本，关联原始请求和委派阶段，不能把同一会话所有工作混在一起 |
| 未提供子节点候选协议 | `AgentInvite` 与 `TeamSay` 发送 `HintBlock`，收件箱转换为 `AssistantMsg`；记忆工具只认可真实 `user` 来源 | 增加结构化候选／证据提交；不得将团队消息改成用户消息以绕过来源检查 |
| 写工具当前直接落库 | `memory/_direct.py:83–103` 校验用户来源后直接调用仓库写入，没有按委派身份暂存候选的分支 | 对正式写入建立唯一后端处理入口，逐候选计算范围；不能全部套用总控权限 |
| 每次答复结束即可能触发学习 | `memory/_direct.py:293–295` 监听 `ReplyEndEvent` | 区分对话暂停等待、阶段完成、业务确认和任务验收，按有效证据增量处理；不等待一个永远不会结束的长会话 |
| 技术成功未细分为业务成功 | 工具追踪会把成功邀请、成功发送团队消息也记为 `tool/success` | 派发成功不等于任务成功，草稿生成不等于发布或验收 |
| 普通学习证据尚未全面重查来源版本 | `LearningRepository.validate_sources` 主要检查合并／技能提炼所引用的记忆；跨节点普通证据没有完整链路 | 补齐原始用户消息、工具调用和正式业务事件的引用与失效处理 |
| 任务编辑器身份绑定不完整 | 独立生成适配器没有登记 `AgentConversation`，而记忆网关以该表绑定查身份 | 建立可被网关验证的业务运行绑定；不根据提示词里的用户／项目 ID 授权 |
| 多节点同源内容不能保证只存一份 | 直接写入请求 ID 包含节点会话；无 `fact_key` 的不同请求可各自新增；学习内容指纹只识别一致内容 | 按原始证据和操作归并，并使用版本控制处理重复、并发和迟到结果 |

## 15. 系统自动规则（2026-09-10 第二阶段，历史记录）

用户进一步批准将逐智能体人工读写范围、学习参与及经验使用配置收敛为系统规则。第 9—12 节的人工默认范围与开关方案仅保留为历史讨论，不作为当前配置依据。

后端根据四个固定职责绑定、真实业务入口和实际祖先链计算范围。公开／内部不参与能力判断。固定主智能体只显示职责说明；业务智能体默认跟随系统，只可选择排除交互学习或禁止交互长期留存。多级调用取共同允许范围，子节点不能绕过上游收紧；原始来源、群聊受众、知识库和正式业务确认仍单独校验。

当前 11 个智能体与上一阶段审计一致，本次授权允许显式转换为自动规则。旧运行授权快照仍保留原范围作为历史证据，既有有效成果不因新交互例外而被删除。完整规则和最终验证以现行操作说明为准。

## 16. 取消全部逐智能体记忆配置（最新授权）

用户明确要求彻底删除逐智能体的记忆与学习配置。外部能力页移除整个「记忆与学习」Tab，编辑智能体窗口也不提供同类配置；“跟随系统／排除交互学习／禁止长期留存”三选项及 `memory_policy` 字段一并删除。

所有主智能体和业务智能体均由系统按固定职责、真实业务入口、用户与项目、原始来源、消息受众和调用关系计算规则。公开／内部只控制可见性。全局「记忆配置」继续管理总开关、来源、模型和运行预算；用户在本次请求中明确提出的不记忆、不学习要求继续沿同一次业务运行传递。

后台群聊学习、正式业务事件、知识库资料授权、初始化草稿限制、调试隔离和协作来源验证仍按现行规则执行。此变更不新增逐智能体例外，也不将被移除的控制转移到编辑窗口。
