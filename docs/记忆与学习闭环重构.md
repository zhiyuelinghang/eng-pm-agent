## 设计约束

三个抽屉只决定归属。事实、偏好、决定、参考、反思、经验、程序性技能是内容类型；产生方式和验证状态各自独立。学习事件保留有界证据，后台模型只能提出候选，不能直接修改已生效记忆。将私人经验发布到项目必须通过管理发布动作；生成模型不选择更广的归属。

技能沿用旧系统的可复用操作文档语义，不把模型生成的脚本自动装成工具。来源文本不是指令，经验不覆盖用户当前要求或项目正式规定。旧学习代码作为兼容资料保留，实际入口统一到新存储，避免双写和双重提炼。

## 运行方式与触发条件

普通事实、偏好、决定、参考由主模型调用 `add_memory` 后直接校验权限、格式并保存。保存成功不依赖分类器、学习模型或向量模型；修改姓名等明确事实已成功保存时，也不会重复触发纠正学习。普通聊天与仅由助手自称成功的回答不自动排队。

| 触发 | 处理 | 运行入口 |
| --- | --- | --- |
| 用户要求复盘、总结经验或提炼方法 | 记录当前用户材料与工具证据，后台提炼候选 | `learn_from_task`、中间件明确复盘识别 |
| 用户纠正上一轮回答 | 保留原回答和真实用户纠正；原回答不能单独作为成功证据 | `capture_learning_turn` |
| 工具失败 | 仅记录素材，不据此推断修复方法 | `on_acting`、`capture_learning_turn` |
| 同一工具在失败后成功 | 关联同归属、同智能体、同会话证据；支持跨轮次修复 | `recent_failures`、`capture_learning_turn` |
| 新完成任务且存在实际成功工具结果 | 附任务状态和工具结果提炼；任务完成标志本身不能证明经验正确 | `capture_learning_turn` |
| 重复操作模式 | 一轮至少 3 次成功工具操作，且同归属模式达到默认 3 次阈值后提炼 | `capture` |
| 人工反馈 | 关联具体记忆与版本记录成功、失败或不适用，原文保留审计 | `learning_feedback`、管理端“实际使用反馈” |
| 人工合并或经验转技能 | 从同归属已验证成果建立新任务；来源失效则取消 | 管理端“合并经验／提炼操作技能” |
| 周期维护 | 每小时检查过期和失败反馈；同归属至少 3 条已验证经验时可排合并任务，同一批版本不重复处理 | `maintain` |

默认每智能体每日最多 30 个自动学习任务，等待／冷却 60 秒，材料预算 16000 字符，模型超时 90 秒；任务最多自动尝试 3 次，包含超时、输出无效和租约失效。超预算素材仍可在管理端查看、手动排队。全局关闭学习会暂停自动记录和提炼；独立的智能体“使用”开关控制已有成果是否参与检索和技能加载。

模型只提出最多 3 条候选，无权指定更大的共享范围，也不能直接覆盖已生效成果。后台调用前后重新检查智能体能力、当前会话身份与项目权限。合并及技能生成还检查来源 ID、版本、归属和有效状态，提交事务会锁定并再次校验来源。

## 与旧功能的对应关系

| 旧机制 | 新实现及改进 |
| --- | --- |
| 保存后再次分类、提取 | 明确记忆直接写入；只有学习任务才调用后台模型，不以二次模型判定阻塞保存 |
| 反思／纠正／错误和成功模式记录 | 持久化 `learning_events`，按三个抽屉绑定身份，保留有界原始证据 |
| Dreamer 分类和经验整理 | `learning_service` 一次模型调用生成结构化反思、经验或技能候选 |
| 经验去重、合并、收紧 | 完整内容及条件／限制／步骤指纹去重；人工或周期合并生成新候选，审核后可停用被替代成果 |
| 模型自评验证、影子技能转正 | 统一候选隔离与带依据审核；不会因重复次数或助手自评自动转正 |
| 衰减及低价值归档 | 默认 90 天或出现当前版本失败反馈时进入复核、暂停召回；人工停用／拒绝保留历史；明确事实不自动衰减删除 |
| 使用强化 | 记录加载次数和最后使用时间；相关性相同时，当前版本的真实成功反馈提供排序依据，最多计 3 个不同反馈者；加载次数不参与可信度判定 |
| 经验编译操作技能及注入 | 统一 `skill` 类型，保留步骤、条件、限制；默认每轮最多匹配 3 条已验证相关技能，与个人资料一起注入，结束后清理临时上下文 |
| 技能生命周期、修订、回退 | 确认／拒绝／停用／修订／回滚及版本历史统一管理；修订和回滚均产生新候选 |
| Wiki 发布 | 旧 `utils/lifecycle.py::_sync_to_wiki` 实际仅 `_ = page; synced += 1`，没有外部调用。新实现提供真实 Markdown 导出，不误报外部同步成功 |
| 长对话压缩 | 保留原压缩能力与独立模型设置；关闭旧后台摘要二次修订，避免同一压缩重复调用模型 |

“已验证”表示存在管理审核依据，并非系统保证经验永远正确。周期复核使用当前配置的时间间隔；失败反馈在下一次小时级维护进入复核。复核前后的使用反馈按版本分别保存，不会借回滚继承旧版本的成功统计。

## 2026-09-08：称呼偏好与账号身份分离

现场检查用户 ID 17 的有效记忆：`profile.name` 为用户自报姓名，`profile.address` 为“雷总”，两条均正确绑定当前业务用户；账号资料显示名与这两个值不同。此前平台上下文用“当前用户”表示显示名，而轻量资料只注入正文、字段和抽屉，没有显式附上已校验的用户归属，造成模型把名称差异理解成身份疑点。

修复位置：平台上下文明确区分登录用户 ID、账号显示名、系统角色；个人资料注入包含后端确认的用户归属，分别标注自报姓名和称呼偏好的语义，并明确名称不同本身不要求额外身份核验。称呼不证明实名、职位或权限，用户当前明确称呼要求优先。相同偏好字段由仓储直接选择当前项目设置，否则使用跨项目用户设置，不再把两种候选同时交给模型判断。后端授权继续使用用户 ID 和项目权限，未改动用户账号或现有记忆内容。
