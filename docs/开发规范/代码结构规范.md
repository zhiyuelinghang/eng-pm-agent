# 代码结构规范

## 1. 总体原则

- 一个模块只承担一个可清楚命名的领域职责。
- 路由、业务编排、纯转换、数据契约、持久化和外部网关应分层，避免相互反向依赖。
- 可复用逻辑必须从页面或路由中提取；仅在单一调用点使用且很短的逻辑可以就地保留。
- 拆分后由上层模块组合依赖，底层模块不得导入路由或页面组件来取回状态。
- 不以“公共工具”为名建立无边界的杂物模块。公共模块应围绕鉴权、序列化、契约等
  稳定职责命名。

## 2. 当前关键边界

### 后端 API

| 文件 | 职责 |
| --- | --- |
| `backend/app/api.py` | 平台通用业务路由，不承载 Agent 会话和工程资料路由 |
| `backend/app/api_common.py` | 鉴权、项目访问校验、序列化、审计等路由公共能力 |
| `backend/app/agent_conversations_api.py` | Agent 目录、会话、消息、确认和流式响应路由 |
| `backend/app/engineering_documents_api.py` | 工程资料、工程知识库、本地附件和资料操作日志路由 |
| `backend/app/agent_api_support.py` | AgentScope 上下文、消息投影、会话与知识问答支撑逻辑 |
| `backend/app/chat_api.py` | 项目群聊与群聊 Agent 编排 |

新路由应进入对应领域模块。不得把已经拆出的 `/agents/catalog` 或
`/engineering-documents` 路由重新放回 `api.py`。

### 数据库交互

`backend/app/database_interaction_contracts.py` 只定义 Pydantic 输入契约和类型；
`backend/app/database_interactions.py` 负责目录、策略校验和受控执行。新增契约先放入
contracts 模块，执行器不得重新堆积输入模型。

### 前端工作区页面

- Vue 页面负责组合组件、状态与用户流程。
- 页面专用类型放在同名目录的 `types.ts`。
- 无副作用的树构建、格式化、标签与投影逻辑放在 `presentation.ts` 等纯函数模块。
- 大段样式必须放入独立 CSS，通过 `<style scoped src="..."></style>` 引入。
- 可独立描述、独立测试或在模板中形成完整区域的交互，应继续拆成子组件或 composable。

当前 `ProjectSetupView.vue` 使用 `project-setup/types.ts`、
`project-setup/presentation.ts` 和独立 CSS；`AiWorkPlatformView.vue` 的基础样式与任务样式
分别存放。后续修改不得把这些内容重新内联。

## 3. 文件规模门禁

统一结构检查由下列命令执行：

```powershell
.\test-all.bat --suite structure
```

规则的唯一可执行来源是 `scripts/check_code_structure.py`：

| 类别 | 默认硬上限 |
| --- | ---: |
| Python、TypeScript、TSX 生产源码 | 1500 行 |
| Vue 单文件组件 | 1500 行 |
| CSS | 1500 行 |
| 测试文件 | 2000 行 |

历史大文件采用显式“只降不升”的规模棘轮。棘轮不是推荐值，而是过渡期上限：

- `api.py`：2500 行；
- `database_interactions.py`：2550 行；
- `ProjectSetupView.vue`：3100 行；
- `AiWorkPlatformView.vue`：2900 行；
- 其他例外以结构检查脚本中的 `FILE_RATCHETS` 为准。

新增文件不得加入例外。现有例外完成拆分后，应同步降低或删除对应棘轮。若一次合理变更
触及上限，应优先提取领域模块、子组件、契约或纯函数；不得仅提高数字使检查通过。

## 4. 拆分判断

出现任一情况，应在同一变更中评估拆分：

- 文件接近其规模上限；
- 一个路由模块包含多个互不相关的 URL 领域；
- 一个 Vue 页面同时维护多个可独立命名的工作流；
- 类型/Schema 占据大量实现文件；
- 纯格式化或树转换逻辑依赖页面局部状态才能复用；
- 测试必须跨越大量无关初始化才能覆盖一个小功能；
- 修改一个功能经常引起不相关区域冲突。

拆分以领域和依赖方向为依据，不按固定行数机械切片。新模块命名应表达业务含义，避免
`utils2.py`、`common_new.ts`、`misc.py` 等无边界名称。

## 5. 依赖方向

推荐依赖方向：

```text
路由/页面 -> 业务编排 -> 领域服务/网关 -> 数据模型或外部服务
          -> 纯转换/契约（不可反向导入路由/页面）
```

- FastAPI `main.py` 只负责应用装配和生命周期，不承载领域路由实现。
- 公共鉴权函数不得导入具体 Agent 或工程资料路由。
- 前端类型与 presentation 模块不得导入 Vue 页面实例或 Pinia store。
- 外部服务调用统一经网关/客户端封装，浏览器不得直接持有服务端密钥。

## 6. 生成物与临时文件

- `dist`、构建缓存、测试缓存和运行数据不作为源码修改提交，除非发布流程明确要求。
- 一次性机械迁移脚本在完成并验证后删除；可长期复用的迁移或检查脚本必须有说明和测试。
- 不修改第三方依赖或上游镜像来规避本项目结构问题。
