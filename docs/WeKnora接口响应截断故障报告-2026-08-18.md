# WeKnora 接口响应截断故障报告

## 1. 问题摘要

- 排查日期：2026-08-18
- WeKnora 接入地址：`http://uy8rk3wy.duankouyingshe.net/api/v1`
- 鉴权方式：`X-API-Key`，密钥已省略
- 稳定复现接口：`GET /knowledge-bases`
- 平台提示：`AgentScope 请求失败（502）：WeKnora 返回的不是有效 JSON。`

同一请求会间歇性成功、返回截断的 JSON、返回 HTML 错误页或超时。直接请求映射域名也能复现，因此故障不在平台前端；当前证据指向 WeKnora 服务、Nginx 或端口映射链路中的响应传输异常。

## 2. 调用链路

```text
工程管理平台 → AgentScope → uy8rk3wy.duankouyingshe.net → Nginx/WeKnora
```

AgentScope 对 WeKnora 返回内容执行 JSON 解析。上游响应被截断或返回 HTML 时，AgentScope 将解析失败转换为 HTTP 502，并向平台返回上述提示。

## 3. 复现结果

### 3.1 经 AgentScope 连续请求

对知识库列表接口连续请求 12 次：

| 结果 | 次数 |
| --- | ---: |
| 成功返回 | 7 |
| 返回内容不是有效 JSON | 4 |
| 请求超时 | 1 |

失败合计 5 次，样本失败率为 `5/12`。该数据仅用于说明问题可以高频复现，不代表长期故障率。

### 3.2 直接请求 WeKnora 映射域名

绕过平台业务接口，直接使用同一 API Key 请求：

`GET http://uy8rk3wy.duankouyingshe.net/api/v1/knowledge-bases`

观察到以下四类结果：

| 场景 | HTTP 状态 | Content-Type | 响应长度 | 耗时 | 说明 |
| --- | ---: | --- | ---: | ---: | --- |
| 正常 | 200 | `application/json; charset=utf-8` | 25,731 字节 | 0.32～4.94 秒 | 可完整解析 |
| 异常一 | 200 | `application/json; charset=utf-8` | 1,097 字节 | 1.36 秒 | JSON 在中间结束，无法解析 |
| 异常二 | 200 | `application/json; charset=utf-8` | 12,099 字节 | 1.20 秒 | JSON 在中间结束，无法解析 |
| 异常三 | 502 | `text/html; charset=utf-8` | 2,675 字节 | 1.99 秒 | 返回端口映射错误页面 |
| 异常四 | 无响应 | 无 | 无 | 12 秒以上 | 读取超时 |

正常和两次截断响应具有相同的 JSON 开头；截断响应仅缺失后半部分。异常响应仍可能携带 `200` 和 `application/json`，因此调用方只能在解析时发现内容不完整。

正常响应与截断响应均观察到 `Server: nginx/1.30.3`。端口映射错误页没有相同的 Server 响应头。

## 4. 当前判断

### 已确认

1. WeKnora 映射地址会间歇性返回不完整的响应体。
2. 部分异常响应错误地保留了 `HTTP 200` 和 JSON Content-Type。
3. 映射地址还会偶发返回 502 HTML 页面和读取超时。
4. AgentScope 的 502 是对上游无效响应的转换结果，并非原始数据被 AgentScope 改坏。

### 基本排除

1. **API Key 或接口路径错误**：完全相同的请求可以正常成功。
2. **前端展示问题**：直接访问 WeKnora 映射地址即可复现。
3. **响应体过大**：正常响应仅约 25 KB。
4. **单纯超时设置过短**：截断响应通常在 1～2 秒内返回。

### 尚需 WeKnora 部署侧确认

目前无法仅从公网映射地址判断响应是在 WeKnora 应用、Nginx，还是端口映射节点被截断。需要结合服务器内部直连测试和服务端日志进一步定位。

## 5. 请 WeKnora 负责人核查

1. 在 WeKnora 服务器本机或同一局域网，绕过公网端口映射，连续请求同一接口至少 100 次。
2. 同时从公网映射地址执行相同测试，对比内部直连和公网映射的结果。
3. 检查 Nginx error log，重点搜索：
   - `upstream prematurely closed connection`
   - `connection reset by peer`
   - `upstream timed out`
   - `recv() failed`
4. 检查端口映射客户端和服务端日志，确认是否存在断线重连、连接数限制、流量限制或响应转发中断。
5. 检查 Nginx 到 WeKnora 上游的 keepalive、代理缓冲、压缩和超时设置。
6. 确认端口映射后是否存在多个后端实例，以及不同实例是否运行相同版本并保持健康。
7. 如条件允许，提供稳定的 HTTPS 域名或可直连地址，避免继续使用不稳定的临时端口映射链路。

## 6. 建议复现命令

以下命令不会在报告中写入真实 API Key：

```bash
curl -i \
  -H "X-API-Key: ${WEKNORA_API_KEY}" \
  -H "Accept: application/json" \
  "http://uy8rk3wy.duankouyingshe.net/api/v1/knowledge-bases"
```

连续测试时需要同时记录：HTTP 状态、Content-Type、响应字节数、总耗时、JSON 是否能完整解析。仅检查 HTTP 200 不足以判断请求成功。

## 7. 修复验收标准

建议至少满足以下条件：

1. 内部直连与正式外部地址分别连续请求 100 次。
2. 100 次均返回 2xx 且响应体可以完整解析为 JSON 对象。
3. 不再出现截断 JSON、HTML 错误页或连接超时。
4. 同一数据未发生变化时，响应结构和主体长度应保持合理稳定。
5. 修复后再由工程管理平台执行知识库列表、目录树、文件读取和问答回归测试。

## 8. 平台侧临时缓解说明

平台可以对列表、目录树等幂等只读请求增加有限次数自动重试，以降低偶发错误对界面的影响。但上传、移动、删除、创建会话和发送问答等写操作不能盲目重试，否则可能造成重复数据。

自动重试只能缓解现象，不能替代 WeKnora 部署链路的修复。
