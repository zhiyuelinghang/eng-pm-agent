## 一、测试方法

测试脚本 `robustness.py` 启动真实的 MCP server 子进程，按 JSON-RPC 协议对话，与生产环境的调用路径完全一致。这样能捕获只在真实运行时暴露的问题——例如日志误写入 stdout 污染协议帧、跨进程的并发竞争。

设计原则是**对抗性**而非确认性：每个功能都刻意寻找边界、矛盾输入与攻击面，目标是让实现暴露与设计意图不符之处。

## 二、发现的缺陷

### 缺陷 1：停机后重启触发风暴 【严重】

**发现路径**：测试「now 早于上次 tick 是否重复创建」时，实际结果 `1 → 2` 与预期不符。追查根因后发现问题远比时间倒流严重。

**问题描述**

`tick` 计算下次触发时刻时，以「本次触发的历史时刻」而非「当前真实时刻」为基准：

```python
plan.next_fire_at = next_fire_after(trigger, after=fire_at, ...)   # fire_at 是历史时刻
```

导致推进后的 `next_fire_at` 仍然停留在过去，下一次 tick 又会补一个历史触发——如此往复，直到追平当前时间为止。

**实测危害**

```
停机 200 天后重启，cron 每分钟 tick：
  1 小时内创建了 50 个任务，并会持续到补满 200 次
```

真实环境中即为 200 条通知在短时间内轰炸责任人，且每条都对应一个早已过期的历史周期。

**为何此前未被发现**

早期压测中有一条「停机不补跑」的用例判定为通过——那是**假阴性**。该用例每次只 tick 一轮就检查结果，恰好只看到第一次触发，未能暴露后续的连锁补发。这说明单次调用的验证不足以覆盖调度类逻辑，必须模拟连续调用。

**修复**

```python
# 以「当前时刻」而非「本次触发时刻」为基准推进，确保下次触发落在未来。
plan.next_fire_at = next_fire_after(
    trigger, after=max(fire_at, moment), fire_count=plan.fire_count,
)
```

**修复后实测**

| 情境 | 修复前 | 修复后 |
|---|---|---|
| 停机 200 天，tick 60 次 | 50 个任务 | **1 个任务** |
| 停机 5 周，tick 60 次 | 35 个任务 | **1 个任务** |
| 时间倒流（NTP 校时） | 重复创建 | **不重复** |

下次触发时刻均正确落在当前时刻之后。

**回归测试**：`test_downtime_does_not_storm_on_repeated_ticks`、`test_clock_going_backwards_does_not_duplicate`

### 缺陷 2：字符串序号被静默接受 【中】

**问题**：`complete_step(seq="0")` 被接受。`int("0")` 静默成功，掩盖了调用方对 schema 的误解。

**风险**：MCP 的调用方多为语言模型，参数类型出错是常见情况。静默转换会让问题延后到更难排查的位置暴露；更危险的是 `seq=True`——Python 中 `isinstance(True, int)` 为真，会被静默当作 `seq=1`，**误操作到错误的节点**。

**修复**：新增 `parse_int()`，明确区分两类问题：

```python
# 类型错误 → 拒绝（调用方误解了 schema，应当立即得知）
if isinstance(value, bool) or not isinstance(value, int):
    raise ToolError(f"{field} 必须是整数，收到 {type(value).__name__}：{value!r}")

# 数值越界 → 夹回边界（意图清楚，不必打断调用方）
if low is not None and value < low:
    return low
```

**例外**：节点序号不做夹回。`seq=-1` 若夹成 `0` 会误操作到另一个节点，必须显式拒绝。

**回归测试**：`test_numeric_string_seq_rejected`、`test_bool_seq_rejected`

---

### 缺陷 3：非法 limit 导致未处理异常 【中】

**问题**：`list_tasks(limit="很多")` 中 `int()` 抛出的 `ValueError` 未被捕获，冒成协议层异常。

**风险**：工具层的参数错误本应作为工具结果返回，让模型看到并自行纠正。冒成协议异常会中断对话流程。

**修复**：统一走 `parse_int()`，返回明确的工具错误。

**回归测试**：`test_invalid_limit_type_reports_error`

---

### 缺陷 4：「每隔一天」未识别为周期 【低】

**问题**：正则只匹配「每N天」，未覆盖口语中同样常见的「每隔N天」，被误判为一次性任务。

**修复**：正则扩展为 `每(?:隔)?`，同时从标题提取逻辑中剥离该前缀。

**回归测试**：`test_meige_phrasing`、`test_meige_prefix_stripped_from_title`

---

### 缺陷 5：「每半个月」未识别 【低】

**问题**：「半」不在数字表中，整条表述被跳过，退化为一次性任务。

**修复**：单独识别并按 **15 天**处理。选择 15 天而非归入「月」，是因为「半个月」的本意是约两周的固定间隔，按月处理会产生 28~31 天的浮动，与用户预期不符。

**回归测试**：`test_half_month`

## 三、验证通过的关键特性

以下特性经对抗性测试确认可靠。

### 3.1 定时触发的精确性

**月末不漂移** — 按月重复时锚定首次触发日，而非在上次结果上迭代：

| 起始日 | 实测触发序列 |
|---|---|
| 2028-01-31（闰年） | 01-31 → **02-29** → 03-31 → 04-30 → 05-31 → 06-30 → 07-31 |
| 2026-01-30 | 01-30 → **02-28** → **03-30** → 04-30 → 05-30 |
| 2026-11-30（每 2 月，跨年） | 2026-11-30 → 2027-01-30 → 03-30 → 05-30 → 07-30 |

关键在于 2 月被夹到月末后，3 月能**回弹**至原始日期。若采用逐次迭代，日期会一路下滑并逐月累积偏差。

**幂等性** — 6 小时内每分钟 tick（360 次），按小时触发的计划恰好产生 6 个任务。

**次数与截止边界** — `max_fires=3` 连续 14 天 tick 恰好 3 次；`until=8/3` 触发 8/1、8/2、8/3 三次（含边界）。

**过去时刻补偿** — 首次触发时刻在过去时，tick 会立即补触发一次（合理：该执行的没执行），但不会补跑整段历史。

### 3.2 流转顺序约束

12 项绕过尝试全部被拦截：

| 尝试 | 结果 |
|---|---|
| 跨越到第 2/4 个节点 | 拒绝，提示当前应处理节点 |
| 超大序号 99999 | 拒绝 |
| 负序号 -1 / -2 | 拒绝 |
| 小数序号 1.5 | 拒绝 |
| 字符串序号 "0" | 拒绝（修复后） |
| 布尔序号 True | 拒绝（修复后） |
| 重复完成已完成节点 | 拒绝 |
| 改派已完成节点 | 拒绝（历史责任归属不可篡改） |
| 阻塞已完成节点 | 拒绝 |
| 跳过必经节点 | 拒绝 |

错误提示明确指出下一步该做什么：

```
当前应处理节点「执行巡检」（第 1 个），不能跨越到「巡检归档」
```

### 3.3 终态防护

已取消/已完成的任务上，`complete_step`、`forward_step`、`accept_task`、`cancel_task` 全部被拒绝。

### 3.4 逾期判定

| 情境 | 结果 |
|---|---|
| 恰好在截止时刻 | 不标记（边界不算逾期） |
| 超过截止 1 秒 | 标记 |
| 重复 tick | 不重复标记 |
| 逾期后完成节点 | 恢复 running，可继续办理 |
| 已闭环任务 | 永不标记 |

### 3.5 并发安全

4 个独立客户端进程访问同一数据库：

| 情境 | 结果 |
|---|---|
| 新任务可见性 | 4 个客户端全部可见 |
| 同时完成同一节点 | **恰好 1 个成功**，其余被拒 |
| 同时 tick 同一到期计划 | **共创建 1 个任务** |
| 重启后 | 任务与历史完整 |

触发幂等由 `fire_log` 表的 `(schedule_id, fire_at)` 主键在数据库层保证，而非依赖应用层判断。

### 3.6 输入攻击面

16 类攻击载荷全部安全处理，数据库始终完好：

SQL 注入、路径穿越、模板注入（`{{7*7}}`、`${jndi:ldap://}`）、JSON 注入、50KB 超长输入、控制字符、零宽字符、RTL 覆盖字符、emoji、繁体、中英混合、换行轰炸。

采用参数化查询，注入载荷仅被当作普通文本存储。

### 3.7 协议健壮性

| 情境 | 结果 |
|---|---|

| 缺 method / method 为数字 | 返回错误，服务存活 |
| params 为数组 / 100 层嵌套 | 返回错误，服务存活 |

## 四、有意为之的设计选择

以下行为在测试中被确认，属于设计决策而非缺陷，在此说明以免误判。

**「每季度」未被识别为周期** — 引擎的间隔单位为 时/天/周/月，无「季度」。该表述退化为一次性任务，符合「认不出就不猜」的保守策略。若业务需要，可扩展为「每 3 月」。

**「每周一和周四」只取第一个** — 引擎的触发模型是「固定间隔」，不支持一周内多个触发点。当前解析为「每周一」。如需支持，应登记两个计划。

**空字符串附件被接受** — `attachments: [""]` 视为已提交。引擎不校验附件内容真实性，因其无法访问文件系统；材料有效性由宿主系统负责。

**路径穿越文件名被接受** — 引擎仅存储字符串引用，不做文件操作。宿主系统在实际读取时应自行校验。

**受阻节点可转办** — 换人往往正是解除阻塞的手段（原责任人不在现场），故允许。

## 五、结论

147 项对抗性测试发现 5 个缺陷，其中 1 个严重级别——停机重启触发风暴。该缺陷在真实环境中会导致大量历史任务被集中补发，直接骚扰责任人，且早期压测因验证方式不足而未能发现。

全部缺陷已修复并补充回归测试。当前状态：

- 鲁棒性测试 **147/147** 通过
- 单元与协议契约测试 **220/220** 通过

引擎的核心不变量——**触发幂等**、**流转顺序**、**留痕完整**、**终态不可变**——在对抗条件下均得到验证。

### 后续建议

1. **部署前确认 cron 频率** — 建议 5 分钟一次。触发精度受此限制，若业务需要分钟级精度需相应调低。
2. **补充「每季度」等表述** — 若实际使用中频繁出现，扩展 `UNIT_MAP` 即可。
3. **接入宿主系统时** — 附件有效性、人员标识合法性需由适配层校验，引擎不承担这部分职责。
