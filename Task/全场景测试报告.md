## 二、发现的缺陷

### 缺陷 1：退回重做可绕过留证约束 【严重】

**发现路径**：测试「退回后节点的旧附件」时，进一步追问「确认人要求重拍，责任人不重拍能否通过」。

**问题描述**

验收退回时，节点的旧附件被完整保留（这本身是对的——审计轨迹不可抹去）。但 `complete_step` 的留证校验是「有附件即可」，导致：

```
1. 张三提交了「整改前拍的.jpg」
2. 确认人退回：照片不清晰，重拍
3. 张三不重拍，直接点完成 → 通过（旧照片顶用）
4. 留证约束在退回场景下被完全架空
```

**危害**：工程场景里「退回重做」最常见的理由就是材料不合格。若旧材料还能顶用，退回就形同虚设，责任追溯链条断裂——确认人要求重拍照片，责任人却不重拍也能闭环。

**根因**：`complete_step` 的留证校验只看「是否已有附件」，没有区分「首次提交」与「退回重做」。

**修复**

引入 `Step.reopened` 标记：退回时置为真，完成时复位。

```python
# 退回时：旧附件保留（审计），但标记重做
step.reopened = True

# 完成时：重做状态下，旧附件不算数
if step.requires_attachment and not files:
    if step.reopened:
        raise TransitionError("节点「整改并拍照」被退回重做，需要重新提交证明材料")
    if not step.attachments:
        raise TransitionError("节点「整改并拍照」要求提交证明材料")
```

**修复后实测**

```
退回后：附件 ['第一次.jpg'] 保留，reopened=True     ← 审计完整
不重拍直接完成 → 拒绝「需要重新提交证明材料」      ← 约束生效
重新拍照完成 → 成功，附件 ['第一次.jpg', '重拍的.jpg']  ← 历史累加
```

首次提交时沿用已上传的附件仍被允许——只有退回重做才强制新材料，语义精确。

**回归测试**：`TestRejectRequiresFreshEvidence` 共 5 个用例，覆盖：旧附件保留、旧附件不可复用、新材料可提交、首次提交豁免、非留证节点不受影响。

**涉及文件**：`domain/models.py`（加字段）、`domain/flow.py`（退回置位 + 完成校验）、`store/schema.sql`（加列）、`store/sqlite.py`（读写）、`serialize.py`（暴露给前端）。

## 三、验证通过的关键特性

### 3.1 责任制三要素（新增能力）

**绕过尝试全部被拦截**：

| 尝试 | 结果 |
|---|---|
| 空字符串 / 纯空格 / 制表符 / 换行 作责任人 ref | 视为未指派，不变成"叫空字符串的人" |
| 三要素缺失的 7 种组合布置 | 全部拒绝，错误信息指明缺什么 |
| `missing_requirements` 数量 | 精确（全缺=3，缺2项=2，缺1项=1，齐备=0） |
| 转办给空 ref / 空白 ref | 拒绝或保持有主，不让任务变无主 |

**模板阶段豁免**：无三要素时创建模板被允许（模板需跨工点、跨人员复用），只有 `dispatch` / `create_schedule` 才强制——设计合理。

**人数少于节点数**：轮转复用，1 人分配 4 节点全部有主。

### 3.2 确认人权限

6 种非确认人身份验收全部被拒：节点责任人、另一责任人、陌生人、大小写变体（`BOSS`）、带空格（` boss `）、姓名而非 ref（`王工`）。

**转办不能转移验收权**——把节点转给某人，不等于把验收权也交给他。这是审计的关键保证。

### 3.3 责任制 × 定时触发

- **不完整的流程无法登记定时计划**——否则缺陷会静默发生在后台 tick 里，没人看得到
- 触发出的任务**完整保留三要素**
- 多次触发的任务**互相独立**（完成 A 不影响 B）

### 3.4 状态机完备性（21 项笛卡尔积）

终态（done / cancelled）下 6 种操作全部拒绝；非终态下的合法操作全部放行，包括「逾期任务仍可办理」「受阻节点完成即恢复运行」这类容易误拒的边界。

### 3.5 并发（责任制场景）

- 4 客户端同时验收 → **恰好 1 个成功**
- 4 客户端同时转办 → 最终是其中之一，数据不损坏
- A 验收后 B 尝试办理 → 拒绝

### 3.6 跨任务隔离

5 个同名任务操作其一、取消其一、同工点任务阻塞其一，均不影响其余任务——id 关联无串扰。

### 3.7 时序漏洞

- 已登记的计划不会被"同 id 覆盖"架空（每次创建新 flow 生成独立 id）
- 同秒内 30 条备注全部记录，历史顺序稳定（非递减）

### 3.8 计划生命周期

暂停不触发、恢复继续、暂停不消耗 `fire_count`、停用后不再触发、`max_fires` 精确、对不存在的计划报错而非崩溃。

### 3.9 边界

- **触发时刻在过去**：任务在同一 tick 内即被标记逾期（不需要等下一轮），且不重复标记
- 历史触发的任务截止时间基于触发时刻推算，立即进入逾期状态

### 3.10 回归不变量（第一轮已验，本轮复核）

停机 200 天不补跑、月末不漂移（1/31→02-28→03-31→04-30→05-31）、同一时刻 tick 20 次只建 1 个任务、跨越节点被拒、留证不传附件被拒、SQL 注入后数据库完好。

### 3.11 性能

200 个带责任制的任务写入 < 60 秒；按工点/确认人/责任人/组合过滤均 < 500ms（实际毫秒级）；库体积 < 10MB。

## 四、测试过程修正

本轮测试过程中有 3 处**测试脚本自身**的判断需要修正（非引擎缺陷），在此说明以免误读：

1. **退回重做的历史条数**：初版断言「> 100 条」，实测 51 条。核查后确认：退回只重开最后一个节点，第 2 轮起每轮只需完成 1 个节点，51 条恰好对应 14 次完成 + 10 次退回重开 + 状态变更 + 创建。审计轨迹完整，是预期值算错了。

2. **历史触发的逾期时机**：初版断言「下次 tick 才标记逾期」，实测任务在**同一次 tick 内**就被标记。这是引擎更好的行为（触发与逾期扫描同轮完成），断言看错了时机。

3. **`finish_all` 辅助函数**：初版按序号重跑所有节点，撞上"已经了结不能重复完成"；改为只完成未了结节点。

## 五、结论

本轮 117 项对抗性测试发现 **1 个严重缺陷**：退回重做可绕过留证约束。该缺陷直接破坏工程管理的责任追溯——确认人要求重做材料，责任人却能不重做就闭环。

已修复并补充 5 个回归测试。当前状态：

- 本轮场景测试 **117/117** 通过
- 累计单元与协议契约测试 **254/254** 通过
- 第一轮鲁棒性测试 **147/147** 通过

核心不变量在对抗条件下全部成立：**触发幂等**、**流转顺序**、**留证强制（含退回重做）**、**验收权限**、**终态不可变**、**跨任务隔离**。
